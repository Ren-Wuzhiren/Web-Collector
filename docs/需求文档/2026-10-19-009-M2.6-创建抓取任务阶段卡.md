### 二级阶段 M2.6：保存链接时创建抓取任务

**一句话**：保存链接时，同一事务创建一条可持久化的 `PENDING` 任务。
**完成标志**：真实 HTTP 保存成功后，响应同时带回 link 和 job；MySQL 中任务可查且初始状态为 `PENDING`。
**预计时长**：一次阶段内分件完成，按测试与迁移结果调整　**依赖**：M2.5 已完成

---

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| Spring `@Transactional` | 协调链接、标签关联和任务写入 | 让三类记录同成同败 | 先写链接再异步补任务会留下“有收藏但永远不采集”的孤儿状态 |
| MySQL + Flyway V9 | 保存持久任务并演进 schema | MySQL 是项目已选的事实队列，随现有事务提交 | Redis 队列不能替代数据库里的可审计任务记录 |
| MyBatis-Plus | 映射 CaptureJob 并插入任务 | 沿用项目 Mapper 模式 | 本步 SQL 简单，不额外引入队列中间件 |

#### 2. 原理讲解（不用它会怎样）

- **事务原子性**：链接、tag 关联和 job 一起提交；若 job 插入失败，整笔回滚。没有同一事务时，客户端可能收到保存成功，但数据库没有采集任务。
- **持久化队列**：`PENDING` 行本身就是待办事实，进程重启后仍在。若只在内存里排队，应用崩溃会丢失任务。
- **事务传播**：推荐由 `LinkService` 开启事务，`CaptureJobService` 使用默认 `REQUIRED` 加入同一事务；若误用 `REQUIRES_NEW`，链接回滚时 job 仍可能留下。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：`LinkController → LinkService → CaptureJobService → CaptureJobMapper → MySQL`。
- **数据流向**：鉴权用户提交 URL → M2.5 规范化与去重 → 校验集合/tag → 插入 link → 写 link_tag → 写关联的 PENDING capture_job → 返回 `{link, job}`。
- **改动边界**：新增 V9、capture 领域的初始持久化、创建响应 DTO；更新 `POST /links`。不实现 Worker、任务状态迁移、抢占、恢复、轮询 API 或前端。
- **为什么放这层**：`LinkService` 负责“保存链接”整体用例与事务；`CaptureJobService` 负责生成符合队列初始契约的任务，避免 LinkService 自己拼任务字段。
- **待确认取舍**：可以让 LinkService 直接调用 CaptureJobMapper，改动更少；代价是链接域直接掌握任务表细节。推荐保留 CaptureJobService 边界，代价是多一层薄服务和事务传播理解成本。

#### 5. 重难语法讲解

- **`@Transactional(propagation = REQUIRED)`**：默认加入当前事务；若调用时没有事务才新开。常见错法是给任务写入单独开 `REQUIRES_NEW`，使链接失败时任务仍提交。
- **Java `record` 响应类型**：用 `LinkCreationResponse(LinkSummary link, CaptureJobSummary job)` 固定对外结构；不要直接返回数据库实体，否则内部字段可能意外暴露。

#### 6. 具体实现

本节是实现契约，由用户完成后端生产代码；Codex 后续编写测试并审查。

##### `backend/src/main/resources/db/migration/V9__create_capture_job.sql`
- **作用**：建立任务表，字段以 `docs/工程化文档/05-数据库设计.md` 的 `capture_job` 设计为准。
- **契约**：包含 `link_id`、`requested_by`、`status`、重试字段、时间/租约/错误字段，以及 `idx_job_claim`、`idx_job_recovery`、`idx_job_link_created`；FK 和级联策略写入前先确认。
- **怎么验证**：Testcontainers 启动 MySQL 后 Flyway 执行到 V9；查询 `information_schema` 确认列、索引和约束。

##### `backend/src/main/java/com/webcollector/capture/`
- **作用**：保存任务实体、初始状态和创建职责。
- **建议契约**：`CaptureJobStatus` 包含 `PENDING/RUNNING/SUCCEEDED/FAILED`；`CaptureJobService.createPending(linkId, requestedBy, now)` 插入 `attempt_count=0`、`max_attempts=3`、`next_attempt_at=now` 的任务并返回摘要。本轮只有 PENDING 创建行为生效，不实现其他状态转换。
- **事务边界**：Service 加入调用方事务（默认 REQUIRED），不使用 `REQUIRES_NEW`。

##### `backend/src/main/java/com/webcollector/link/`
- **作用**：将新链接、标签关联、任务创建组合成一次用户用例。
- **建议签名**：`LinkCreationResponse LinkService.createLink(CreateLinkRequest request)`；Controller 仍返回 `201 Created`，data 改为 `{ "link": ..., "job": ... }`。
- **顺序**：保留 M2.5 重复 URL 的 409 行为；link 与 tag 写入成功后创建 job。任何异常都由同一事务回滚。

##### 测试文件
- **作用**：证明任务初值、响应结构和真实事务链路。
- **至少覆盖**：创建后恰有一条关联 link 的 PENDING job；job 的 owner/status/attempt/nextAttemptAt 正确；重复 URL 返回 409 且不新建 job；不同用户保存相同 URL 各自得到 job；job 写入失败时 link/tag 不残留。

#### 7. 计算机四大件映射

- **映射到**：本步不强行映射到四大件。
- 事务提交、持久化队列属于数据库一致性与应用架构；Worker 并发抢占留到 M3.2 再联系锁与并发机制。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ link 提交后再单独插 job → job 失败时留下不可采集的链接 → 两者放进同一事务。
- ❌ `next_attempt_at` 写成 NULL → 后续领取查询无法命中任务 → 初始时间设为同一 `now`。
- ❌ 给 `link_id` 加唯一约束 → 未来同一链接无法建立新的采集尝试 → 本表只建普通 `(link_id, created_at)` 索引。
- ❌ M2.6 顺手实现 Worker 或重采集接口 → 混入 M3 状态机和后续接口决策 → 本轮只创建首次 PENDING 任务。
