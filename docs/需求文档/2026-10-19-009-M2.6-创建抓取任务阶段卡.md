#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| Spring `@Transactional` | 协调链接、标签关联和任务写入 | 让三类记录同成同败 | 先写链接再异步补任务会留下“有收藏但永远不采集”的孤儿状态 |
| MySQL + Flyway V9 | 保存持久任务并演进 schema | MySQL 是项目已选的事实队列，随现有事务提交 | Redis 队列不能替代数据库里的可审计任务记录 |
| MyBatis-Plus | 映射 CaptureJob 并插入任务 | 沿用项目 Mapper 模式 | 本步 SQL 简单，不额外引入队列中间件 |

#### 2. 原理讲解（不用它会怎样）

- **事务原子性**：一次请求里的链接、标签关联、任务三条写入要么全成、要么全败，解决的是“部分成功”这种半截数据。不用它：链接插进去了、任务插入失败，客户端却收到 201，这条收藏永远不会被采集，也没有任何地方会回头补。
- **持久化队列**：`PENDING` 行本身就是待办事实，解决的是“任务在进程重启后还在不在”。不用它：任务只放内存队列，应用一重启，用户点了保存但抓取任务凭空消失，且没有任何记录可查。
- **事务传播**：`REQUIRED` 让被调用方加入调用方已开启的事务，解决的是“两层服务各开各的事务”。不用它（改成 `REQUIRES_NEW`）：任务在独立事务里提交，链接回滚时任务却留下来，Worker 会去抓一条数据库里不存在的链接。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：`LinkController → LinkService → CaptureJobService → CaptureJobMapper → MySQL`。
- **数据流向**：鉴权用户提交 URL → M2.5 规范化与去重 → 校验集合/tag → 插入 link → 写 link_tag → 写关联的 PENDING capture_job → 返回 `{link, job}`。
- **改动边界**：新增 V9、capture 领域的初始持久化、创建响应 DTO；更新 `POST /links`。不实现 Worker、任务状态迁移、抢占、恢复、轮询 API 或前端。
- **为什么放这层**：`LinkService` 负责“保存链接”整体用例与事务；`CaptureJobService` 负责生成符合队列初始契约的任务，避免 LinkService 自己拼任务字段。
- **已定**：`LinkService` 开启事务，`CaptureJobService.createPending` 用默认 `REQUIRED` 加入；不让 `LinkService` 直接拼任务字段。代价是多一层薄服务和一次事务传播的理解成本。

#### 5. 重难语法讲解

- **`@Transactional(propagation = Propagation.REQUIRED)`**
  - 标准写法：`@Transactional` 等价于 `@Transactional(propagation = Propagation.REQUIRED)`，本步不写参数、直接用默认值即可。
  - 参数含义：`REQUIRED` 表示“有事务就加入，没有就新开一个”；注解本身不决定回不回滚，抛不抛 `RuntimeException` 才决定。
  - 常见错法：给任务写入单独标 `REQUIRES_NEW` → 链接失败回滚时任务已经提交 → 数据库里留下指向不存在链接的任务。
- **Java `record` 作为响应类型**
  - 标准写法：`public record LinkCreationResponse(LinkSummary link, CaptureJobSummary job) {}`。
  - 参数含义：两个字段都是既有的 DTO，record 只负责把它们组合成一个不可变的对外结构。
  - 常见错法：直接返回 `Link` 与 `CaptureJob` 实体 → 把 `user_id`、`locked_by` 这类内部字段暴露给前端。

##### `backend/src/main/java/com/webcollector/capture/`
- **作用**：保存任务实体、初始状态和创建职责。
- **建议契约**：`CaptureJobStatus` 包含 `PENDING/RUNNING/SUCCEEDED/FAILED`；`CaptureJobSummary` 承载 `jobId/linkId/status/attemptCount/nextAttemptAt`；`CaptureJobService.createPending(linkId, requestedBy, now)` 插入 `attempt_count=0`、`max_attempts=3`、`next_attempt_at=now` 的任务并返回摘要。本轮只有 PENDING 创建行为生效，不实现其他状态转换。
- **事务边界**：Service 加入调用方事务（默认 REQUIRED），不使用 `REQUIRES_NEW`。

##### `backend/src/main/java/com/webcollector/link/`
- **作用**：将新链接、标签关联、任务创建组合成一次用户用例。
- **建议签名**：`LinkCreationResponse LinkService.createLink(CreateLinkRequest request)`；Controller 仍返回 `201 Created`，data 改为 `{ "link": ..., "job": ... }`。
- **顺序**：保留 M2.5 重复 URL 的 409 行为；link 与 tag 写入成功后创建 job。任何异常都由同一事务回滚。

##### 测试文件
- **作用**：证明任务初值、响应结构和真实事务链路。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ link 提交后再单独插 job → job 失败时留下不可采集的链接 → 两者放进同一事务。
- ❌ `next_attempt_at` 写成 NULL → 后续领取查询无法命中任务 → 初始时间设为同一 `now`。
- ❌ 给 `link_id` 加唯一约束 → 未来同一链接无法建立新的采集尝试 → 本表只建普通 `(link_id, created_at)` 索引。
- ❌ M2.6 顺手实现 Worker 或重采集接口 → 混入 M3 状态机和后续接口决策 → 本轮只创建首次 PENDING 任务。
