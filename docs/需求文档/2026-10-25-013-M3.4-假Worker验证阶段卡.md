### 二级阶段 M3.4：用假 Worker 验证并发与恢复

**一句话**：用不访问真实网页的假 Worker 把任务领取、成功、失败、退避和租约恢复串起来。
**完成标志**：可控处理器能证明同一任务不会被重复消费，失败和崩溃恢复路径都能稳定重放。
**实施状态（2026-10-27）**：工程实现与自动化验收完成；全量测试 244 项通过。学习验收待用户回答。
**预计时长**：一次实现会话　**依赖**：M3.3 已完成

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| JUnit 5 | 驱动假 Worker 场景 | 可以控制准备、执行和断言顺序 | 直接启动真实网页 Worker 会把网络、浏览器和任务状态混在一起 |
| Java `ExecutorService` | 模拟多个 Worker | 能稳定控制并发数量和等待边界 | 手写线程生命周期容易泄漏，`CompletableFuture` 在本步不是必须 |
| `CaptureJobService` | 调用领取、收尾、恢复能力 | 复用 M3.1/M3.2/M3.3 已验收的任务规则 | 不新增 HTTP 层，避免把调度验证误变成接口设计 |

#### 2. 原理讲解（不用它会怎样）

- **假 Worker**：只模拟“领取任务并执行一个可控结果”，不访问网页。不用它：真实抓取失败时很难判断是网络问题、浏览器问题还是任务状态问题。
- **可控失败注入**：Worker 明确返回成功、失败或崩溃三种结果。不用它：只能测成功路径，无法稳定触发退避和锁超时恢复。
- **并发屏障**：多个 Worker 先准备好，再同时开始领取。不用它：测试可能只是顺序执行，无法证明并发语义。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：`测试假 Worker → CaptureJobService → CaptureJobMapper → MySQL`。
- **数据流向**：

```text
准备 PENDING 任务
  → 假 Worker 并发 claimNext
  → 注入成功：complete
  → 注入失败：fail，等待 next_attempt_at 后再次 claim
  → 注入崩溃：不调用收尾，手动推进 locked_until
  → recoverExpiredJobs
  → 再次 claim，验证任务恢复且不会重复成功收尾
```

- **改动边界**：新增测试用假 Worker/测试辅助类和 M3.4 测试；不接真实网页、不新增数据库迁移、不新增 HTTP 接口。
- **为什么放测试层**：M3.4 的目标是验证已有任务规则组合，而不是提前设计生产调度器。

#### 5. 重难语法讲解

- **`ExecutorService` 生命周期**：使用 `try/finally` 关闭线程池；测试超时后也不能留下后台线程。
- **`CountDownLatch`**：一个 latch 等待 Worker 准备完成，另一个 latch 同时放行；不要用固定 `sleep` 代替同步。
- **结果对象**：假 Worker 返回结构化结果，不用字符串判断“成功还是失败”；这样断言能直接检查 jobId、状态和错误码。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ 用 `Thread.sleep` 等 Worker 同步 → 测试偶发通过或超时 → 用 latch 和有限 `Future#get`。
- ❌ 假 Worker 直接改数据库状态 → 绕过 Service 规则 → 只调用 `claimNext/complete/fail/recoverExpiredJobs`。
- ❌ 崩溃分支仍调用 `fail` → 测不到租约恢复 → 崩溃分支只领取、不收尾。
- ❌ 把手动重采集一起塞进来 → API 和新任务语义膨胀 → 本步只验证假 Worker。

**能讲（Codex 先示范，用户随后合上材料作答）**
- [x] Q1：为什么 M3.4 先用假 Worker，而不是直接接 Playwright？

  > **参考示范**：假 Worker 把任务状态问题和网页采集问题隔离开；先证明领取、并发、失败和恢复规则本身正确，后续接 Playwright 时出现失败才能定位到采集层，而不是两层同时排查。

- [x] Q2：假 Worker 的“崩溃”为什么不能调用 `fail`？
