## 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| Docker Engine / Docker Desktop | 构建镜像、运行容器 | 让 MySQL、Redis、后端和前端从同一份配置启动 | 直接在宿主机手工安装全部依赖：环境差异大，无法形成可复现验收 |
| Dockerfile 多阶段构建 | 后端和前端镜像 | 构建工具留在 builder stage，运行镜像只保留产物 | 单阶段镜像：体积更大，构建依赖进入运行环境 |
| Docker Compose | 四服务编排、健康检查、数据卷和网络 | 当前是单机自托管 MVP，复杂度合适 | Kubernetes：当前规模没有集群调度需求，学习与运维成本过高 |
| Nginx | 静态前端和 `/api/` 反向代理 | 同源访问减少前端跨域配置，并能承载 SPA 路由回退 | 只运行 Vite Preview：不适合作为自托管运行形态 |
| MySQL 8.4 | 业务事实来源 | 用户、链接、任务和资产记录已经持久化在这里 | 只用容器临时文件：重启后数据丢失 |
| Redis 7.4 | 会话、限流和短时协调 | 已有 Redis 和 Sa-Token 基础，限流需要原子计数和 TTL | 用应用内 Map：多实例失效，重启丢状态；数据库计数：每次请求增加写压力 |
| PowerShell 7 | 备份、恢复和验收脚本 | 当前开发与部署验收环境是 Windows | 临时手输多条命令：遗漏目录或参数时难以复现 |
| Testcontainers Redis | 限流集成测试 | 验证真实 Redis 命令语义、TTL 和故障行为 | 只用 Mockito：无法证明原子计数和真实连接失败处理 |

## 2. 原理讲解（不用它会怎样）

- **【镜像与容器】**：镜像是只读运行模板，容器是镜像启动后的运行实例。不用它会怎样：把容器重启误认为重建镜像，或把容器内临时修改当成已经持久化。
- **【Registry 与构建上下文】**：Registry 提供基础镜像；构建上下文是发送给 Docker daemon 的目录。`COPY` 只能读取上下文内文件。不用它会怎样：把 Docker Hub 超时误判成 Dockerfile 写错，或构建时漏拷 `pom.xml`。
- **【数据卷与可恢复性】**：命名数据卷让容器替换后数据仍存在，但“还在”不等于“可恢复”。不用备份会怎样：误删卷、数据库损坏或迁移失败后没有独立副本。
- **【一致性备份】**：数据库备份必须使用一致性快照或事务导出，同时覆盖数据库记录引用的资产目录。不用它会怎样：SQL 里存在 asset 记录，文件却缺失；恢复后页面出现坏资产。
- **【固定窗口限流】**：同一 scope 和 subject 在一个时间窗口内累计请求，达到上限后返回 429。计数与 TTL 必须原子设置，否则并发请求可能绕过上限或产生永久 key。
- **【客户端身份】**：只有来自受信任 Nginx 的转发头才能参与客户端 IP 判断。不用它会怎样：客户端伪造 `X-Forwarded-For` 后切换身份，绕过 IP 限流。
- **【失败关闭】**：限流依赖 Redis，Redis 不可用时选择拒绝受保护请求并返回稳定错误，而不是静默放行。不用它会怎样：Redis 故障期间所有登录、注册或保存接口失去保护。

## 3. 架构讲解（这一步在整体里占哪个位置）

- **运行拓扑**：浏览器 → Nginx 前端容器 → `/api/` 反向代理 → backend 容器 → MySQL / Redis；backend 内调度器领取 `capture_job` 并执行 Playwright 采集；资产与抓取工作目录写入 `capture_data` 卷。
- **独立验收项目名**：`webcollector-m8-acceptance`，宿主机端口 `18080`。独立项目名避免误操作已有 `webcollector` 数据卷。
- **M8.1 数据流**：Compose 启动 MySQL 和 Redis → 健康检查通过 → backend 启动并执行 Flyway → Nginx 启动 → 浏览器访问 18080 → `/api/` 转发到 backend。
- **M8.2 备份数据流**：backend 使用 `/data/assets` 和 `/data/capture-work` → 备份脚本在 MySQL 容器内执行 `mysqldump` → `docker compose cp` 复制两类目录 → 恢复时先停止写入，再恢复 SQL 和文件 → 重启后比对标记数据与 SHA-256。
- **M8.3 请求数据流**：请求进入 Spring MVC → `ClientIpResolver` 得到可信客户端 IP → 按接口选择 scope 和 subject → `RateLimitService` 在 Redis 原子累计并设置 TTL → 超限抛业务异常 → 全局异常处理映射 HTTP 429 与 `Retry-After`。
- **改动边界**：允许修改 Docker/CI/备份等工程工具和限流测试、文档；限流后端生产代码由用户实现；不新增数据库表或 Flyway 迁移；不改 M3 任务抢占语义和 M9 真实 URL 验收口径。
- **为什么放这层**：容器负责运行边界，Nginx 只做入口和代理，应用负责业务限流与错误契约，MySQL/Redis 各自承担事实数据和短时状态。把限流放 Nginx 无法按登录用户 scope 区分；把备份只做在应用内无法覆盖整个数据面。

## 5. 重难语法讲解

- **【`docker build` 与 `docker compose up --build`】**：`docker build` 只生成镜像；`compose up --build` 会先构建再启动。只运行 `docker compose config` 只能校验配置解析，不能证明镜像可构建或服务可用。
- **【`-f` 与 `--env-file`】**：`-f deploy/docker-compose.yml` 选择编排文件，`--env-file deploy/.env` 选择变量来源。常见错法：在当前目录自动探测到错误 `.env`，导致变量缺失或连接到非验收项目。
- **【`docker compose exec -T` 与 `cp`】**：`exec -T` 禁止分配 TTY，适合脚本管道；`cp` 用于在容器和宿主机之间复制文件。常见错法：用 PowerShell 文本重定向改写 SQL 编码，造成备份字节变化。
- **【Compose project name】**：`-p webcollector-m8-acceptance` 隔离容器、网络和命名卷。常见错法：验收命令漏掉项目名后误用生产/开发卷。
- **【Redis 原子窗口】**：计数与过期时间要在同一 Lua 脚本、事务或等价原子操作中完成。常见错法：`INCR` 成功但 `EXPIRE` 失败，留下无 TTL 的永久 key。
- **【可信代理头】**：只有直连来源属于配置中的 trusted proxy 时才读取 `X-Forwarded-For`。常见错法：优先使用最左侧任意客户端提供的值。

## 6. 具体实现

### 部署与备份工具

##### `deploy/docker-compose.yml`

- **作用**：编排 MySQL、Redis、backend 和 frontend，并定义健康检查与命名卷。
- **契约**：验收使用 project name `webcollector-m8-acceptance` 和宿主机端口 `18080`；不得通过配置存在替代真实 `build`、`up` 和页面操作。
- **怎么验证**：查看 `docker compose ps`、health 状态、Nginx 页面和 `/api/v1/health/live`、`/api/v1/health/ready`。

**M8.1 验收结果（2026-11-08）**：backend 5.01 GB、frontend 97.6 MB 镜像构建成功；四个服务在 `webcollector-m8-acceptance` 和 18080 稳定运行；首页、live、ready 均为 200；`example.com` 保存任务一次尝试成功并生成 HTML/PDF/SCREENSHOT 三个资产与 905 字符正文；无 `-v` 停止重启后数据库标记数据和 3 个资产文件仍存在。首次启动发现的 MySQL 临时实例假健康问题已通过 TCP healthcheck 修复。

##### `deploy/backup.ps1`、`deploy/restore.ps1`

- **作用**：完成数据库、资产目录和抓取工作目录的可重复备份恢复。
- **契约**：脚本需要明确 `ComposeFile`、`EnvFile` 和 `ProjectName`；数据库通过容器内 `mysqldump` 备份，目录通过 `docker compose cp` 复制；恢复前要求停止写入；备份清单记录逐文件 SHA-256。
- **怎么验证**：记录恢复前后的标记用户、链接、任务、资产数量与 SHA-256，完成恢复和重启后再次比对。

**M8.2 验收结果（2026-11-08）**：脚本行为测试 6 项通过。独立栈创建用户 `m8r2-47873f0df7`、链接、任务和 3 个资产，并写入抓取目录标记；备份后修改链接标题、删除一条资产记录并覆盖两类文件。恢复后数据库记录、资产/抓取文件 SHA-256 全部回到基线；不带 `-v` 重启后再次一致，18080 首页和 ready 均为 200。

### M8.3 限流公开契约

##### `ErrorCode`

- **新增值**：`RATE_LIMITED`。
- **HTTP 映射**：429。
- **响应边界**：沿用现有统一错误响应和 requestId，不泄露 Redis key、内部计数实现或敏感 subject。

##### `RateLimitProperties`

- **作用**：承载登录、注册、创建链接三类策略的开关、上限和窗口秒数。
- **默认策略**：登录 `10/60s/IP`；注册 `5/600s/IP`；创建链接 `30/60s/用户`。

##### `RateLimitService`

- **方法签名**：`requireAllowed(scope, subject)`。
- **关键伪代码**：

```text
key = 固定前缀 + scope + subject + 当前窗口标识
在 Redis 中原子执行计数递增并在首次计数时设置窗口 TTL
若 count <= limit，则允许
否则计算剩余等待秒数，抛出 RATE_LIMITED 并携带 Retry-After
Redis 不可用时抛出稳定业务错误，默认不放行受保护请求
```

- **关键 3 行**：
  - scope 由受保护接口固定选择，不能信任客户端传入。
  - subject 对匿名登录/注册使用可信客户端 IP，对创建链接使用当前用户 id。
  - 计数和 TTL 必须原子完成。

##### `ClientIpResolver`

- **方法签名**：`resolve(request)`。
- **关键规则**：直连来源是可信代理时才读取转发头；不信任任意客户端写入的 `X-Forwarded-For`；非法或缺失地址有稳定降级规则。

## 8. 坑（会怎么错，不是要注意什么）

- ❌ 只运行 `docker compose config` 就写“全栈启动通过” → 镜像未构建、服务未运行 → 必须执行真实 `build`、`up`、健康检查和页面闭环。
- ❌ Docker Hub 超时后反复删卷或修改所有 Dockerfile → 根因仍未定位 → 按 daemon、registry、基础镜像、依赖和构建上下文逐层诊断。
- ❌ 验收时漏写 `-p webcollector-m8-acceptance` → 命中共用项目容器或卷 → 所有 Compose 命令显式指定项目名。
- ❌ 备份只有 SQL → 恢复后 asset 记录存在但文件缺失 → SQL、资产目录和抓取目录同时备份与比对。
- ❌ 恢复时读取者仍在写 → 恢复后的记录和文件被并发修改 → 先停止 backend/worker 写入，恢复后重启。
- ❌ `INCR` 与 `EXPIRE` 非原子 → Redis key 永久存在或并发绕过 → 使用原子脚本并做真实 Redis 集成测试。
- ❌ 直接信任 `X-Forwarded-For` → 用户伪造多个 IP 绕过限流 → 仅信任已知代理来源。
- ❌ Redis 故障时 catch 后放行 → 安全边界整体失效 → 默认失败关闭并返回稳定错误。
