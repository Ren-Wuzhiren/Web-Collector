### 二级阶段 M4.1：让一个网页能被存成 HTML

**一句话**：Worker 领取任务后，用 Playwright 打开一个公开 HTTP/HTTPS 页面，把渲染后的 HTML 保存到磁盘。
**完成标志**：给定公开页面 URL，测试能完成一次真实导航，并在临时目录中查到非空 HTML 文件。
**实施状态（2026-10-27）**：工程实现与 M4.1 测试验收完成；用户已确认 Playwright HTML 测试通过。
**预计时长**：一次实现会话　**依赖**：M3.4 已完成；M3.4 文档与提交需先收口

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| Playwright Java | 启动 Chromium、导航页面、读取渲染后 HTML | 能处理脚本渲染页面，和后续截图/PDF复用浏览器上下文 | `HttpClient` 只能拿原始响应，拿不到 JS 执行后的 DOM |
| Chromium | M4.1 测试运行时 | 真实浏览器才能验证页面渲染链路 | 不用浏览器无法覆盖 SPA 和脚本生成内容 |
| `java.nio.file.Files` | 写入临时 HTML 文件 | 使用标准文件 API，M4.1 只验证资产落盘，不提前引入 asset 表 | 先建资产表会把 M4.1 和 M5.1 的职责混在一起 |

#### 2. 原理讲解（不用它会怎样）

- **浏览器导航**：先创建 Page，再等待导航完成，最后读取 `page.content()`。不用它：只保存服务器原始 HTML，动态页面内容可能为空。
- **浏览器资源释放**：Browser、Context、Page 必须在 `finally` 中关闭。不用它：测试多跑几次后 Chromium 进程和临时资源会泄漏。
- **临时目录隔离**：每个测试使用独立临时目录。不用它：测试之间共享文件，可能把上一次的 HTML 误判成当前结果。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：`Worker/采集服务 → BrowserHtmlCapture → Playwright → 文件系统`。
- **数据流向**：

```text
CaptureJob 已被领取
  → BrowserHtmlCapture.capture(url, outputPath)
  → 创建 Playwright Browser/Context/Page
  → page.navigate(url)
  → 读取 page.content()
  → 写入 outputPath
  → 返回 HTML 文件路径/结果
```

- **改动边界**：新增 Playwright 依赖、HTML 捕获组件和真实浏览器测试；不做 PDF、截图、正文抽取、SSRF、资产表、HTTP 接口或定时 Worker。
- **为什么放这层**：浏览器生命周期和文件写入属于采集基础设施；不要让 `CaptureJobService` 直接操作 Playwright，否则任务状态和采集实现会耦合。

#### 5. 重难语法讲解

- **Playwright 生命周期**：`try (Playwright playwright = Playwright.create())` 只负责 Playwright 对象；Browser、Context、Page 也必须显式关闭。
- **`page.navigate` 与 `page.content`**：前者触发导航，后者读取当前 DOM 序列化结果；不要把 `navigate` 返回值误当作页面 HTML。
- **`Files.writeString`**：指定 UTF-8 写入临时路径；不要使用平台默认字符集，避免中文页面断裂。

#### 6. 具体实现

本节先锁定实现契约；生产代码由用户完成，Codex 随后补完整测试代码并在聊天窗口同步展示。

##### `backend/pom.xml`
- **作用**：加入 Playwright Java 依赖，锁定版本。
- **契约**：依赖只服务于 `capture` 采集组件；浏览器二进制安装由开发环境或测试准备步骤负责。

##### `backend/src/main/java/com/webcollector/capture/browser/BrowserHtmlCapture.java`
- **建议签名**：

```java
public interface BrowserHtmlCapture {
    Path capture(String url, Path outputPath);
}
```

- **实现契约**：创建 Chromium、BrowserContext 和 Page；导航 URL；读取 `page.content()`；以 UTF-8 写入目标路径；任何异常释放浏览器资源后原样抛出。
- **本步限制**：调用方必须传入已确认的 HTTP/HTTPS URL；SSRF 和重定向复检属于 M4.4。

##### `backend/src/test/java/com/webcollector/capture/browser/BrowserHtmlCaptureTest.java`
- **测试契约**：
  - 启动本地 `HttpServer` 返回带脚本的 HTML，验证保存内容包含脚本执行后生成的 DOM。
  - 使用 JUnit 临时目录，验证文件存在且大小大于 0。
  - 增加一个公开页面冒烟测试，但不把外网不稳定作为唯一验收依据。
  - 测试结束后关闭 HTTP Server 和 Playwright 资源。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ 只用 Java `HttpClient` 下载响应 → 动态页面正文为空 → M4.1 使用 Playwright 读取渲染后 DOM。
- ❌ 每次测试启动浏览器但不关闭 → Chromium 进程泄漏 → 使用 `try/finally` 清理所有资源。
- ❌ 测试只访问外网 → 网络抖动导致验收不稳定 → 本地 HTTP 夹具作为主测试，公开页面只做冒烟。
- ❌ 现在就写 SSRF 拦截 → M4.1 范围膨胀 → 记录输入边界，M4.4 再实现安全策略。
- ❌ 现在就写 asset 表 → M4.1 和 M5.1 混在一起 → 本步只验证文件落盘。

- [ ] Q1：为什么 M4.1 的主测试要使用本地 HTTP 夹具，而不是只访问一个公开网站？

  > **参考示范**：本地夹具能稳定控制 HTML、脚本和响应时间，失败时能判断是采集代码问题；公开网站受网络、限流和内容变化影响，只适合做补充冒烟测试。

- [ ] Q2：为什么 M4.1 先保存 HTML 文件，不立即写 `asset` 表？

  > **参考示范**：M4.1 先证明浏览器能把页面变成可回看的 HTML 文件；`asset` 表涉及路径、哈希、MIME、权限和版本，属于 M5.1，提前混入会让本步无法独立验收。
