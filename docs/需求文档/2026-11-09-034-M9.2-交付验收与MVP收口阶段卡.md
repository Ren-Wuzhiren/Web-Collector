#### 2. 原理讲解（不用它会怎样）

- **【角色即时读取】**：每次管理员请求都从 `app_user.role` 读取角色。只缓存登录时的角色会让数据库提升无法即时生效，也会让降权延迟。
- **【注册关闭】**：账号创建完成后关闭公开注册，接口返回 `403 REGISTRATION_DISABLED`。不关闭时，长期实例会保留不需要的注册攻击面。
- **【持久化与备份分离】**：数据卷负责正常运行时的持久化，备份负责误删、迁移和恢复。只有数据卷会在执行 `down -v` 时被删除。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：运维脚本 → Docker Compose → MySQL `app_user`；浏览器 E2E → Nginx → Controller → Service → MySQL/Redis/Worker。
- **数据流向**：注册 `admin` → 提升 `USER` 为 `ADMIN` → `/auth/me` 返回角色 → 关闭注册并重建 backend → 重启 Compose 后再次验证角色。
- **改动边界**：只改验收脚本、E2E 契约、版本声明、交付文档和本地运行配置；不改业务 API、表结构、迁移或既有数据卷。
- **为什么放这层**：管理员初始化应通过受控运维入口完成；网页公开提权会让任何登录用户尝试突破权限边界。

#### 5. 重难语法讲解

- **【PowerShell 参数化 Compose】**：`docker compose -p $ProjectName --env-file $EnvFile -f $ComposeFile exec -T mysql ...`；三个定位参数共同决定连接哪个项目，缺少 `-p` 可能操作到错误数据卷。
- **【角色条件更新】**：更新条件包含 `role = 'USER'`，随后回查必须为 `ADMIN`；只执行无条件更新会掩盖异常角色值。
- **【Playwright 外部服务】**：设置 `E2E_BASE_URL` 时 `webServer` 关闭；测试应验证生产资源特征，而不是假设外部地址永远为 4173。

#### 6. 具体实现

##### `scripts/promote-admin.ps1`

- **作用**：对指定 Compose 项目的账号执行受控、幂等的 `USER -> ADMIN` 提升。
- **接口**：

```powershell
.\scripts\promote-admin.ps1 `
  -Username admin `
  -ComposeFile .\deploy\docker-compose.yml `
  -EnvFile .\deploy\.env `
  -ProjectName webcollector
```

- **关键契约**：不读入或输出密码；账号不存在失败；已是 ADMIN 幂等成功；异常角色失败；更新后回查。
- **怎么验证**：真实 MySQL 脚本测试覆盖正式参数、幂等提升、缺失账号和凭据不泄漏。

##### `scripts/promote-demo-admin.ps1`

- **作用**：保留原本地开发入口，内部代理到通用脚本。
- **关键契约**：默认目标仍为 `deploy/local/docker-compose.yml` 的本地 MySQL。
- **怎么验证**：现有提升与缺失账号测试继续通过。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ 用默认 Compose 项目执行管理员更新 → 可能写进其他项目的数据卷 → 显式传 `-p`、`--env-file` 和 `-f`。
- ❌ 提升前就关闭注册 → 新实例无法创建首个管理员 → 先创建并提升，再关闭注册。
- ❌ 重启时使用 `down -v` → 用户和资产被删除 → 只使用不带 `-v` 的 `down`。
- ❌ 把测试端口写死为 4173 → 正式栈全部前端用例被错误阻断 → 用生产资源特征和可选端口断言。
