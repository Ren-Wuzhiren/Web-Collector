### 二级阶段 M3.2：多 Worker 任务抢占

**一句话**：多个 Worker 同时取任务时，各自拿到不同的到期 `PENDING` 任务。
**完成标志**：两个 Worker 并发争抢一条任务时只有一方成功；有两条任务时双方各领一条。

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| MySQL 8.4 InnoDB | 行锁与任务抢占 | `FOR UPDATE SKIP LOCKED` 让一个事务跳过已被其他事务锁住的行，多个 Worker 不必排队等同一任务 | Redis 队列不能替代 `capture_job`：任务状态和审计事实仍应保存在 MySQL |
| MyBatis Mapper 原生 SQL | 选出下一条任务并条件更新 | 抢占 SQL 包含锁子句和指定排序，直接写 SQL 比拼接 Wrapper 更清楚 | `selectList` 后再 Java 过滤：查询与修改分离，无法表达数据库行锁 |
| Spring `@Transactional` | 让锁定查询和更新同成同败 | 行锁要一直持有到任务已改成 `RUNNING` 后事务提交 | 两个独立事务：查询释放锁后，其他 Worker 可能再次选中同一行 |

#### 2. 原理讲解（不用它会怎样）

- **行级排他锁**：`SELECT ... FOR UPDATE` 锁住候选行，其他事务不能同时修改它。不用它：两个 Worker 都先查到同一条 `PENDING`，然后都认为自己可以开始抓取。
- **`SKIP LOCKED`**：查询遇到已被别的事务锁住的行时直接跳过，继续看下一行。不用它：多个 Worker 会阻塞等待同一行，吞吐量下降；即使最终只有一个能更新，也会产生无意义的锁等待。
- **短事务**：只在“选任务 + 改成 RUNNING”期间持有数据库连接和行锁，真正抓网页发生在事务提交之后。不用它：一条慢网页会把连接和锁占住几十秒，其他 Worker 和连接池都被拖住。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：`未来的 Worker → CaptureJobService → CaptureJobMapper → MySQL`。
- **数据流向**：

```text
claimNext(workerId, lockedUntil)
  → SELECT 一条 PENDING 且 next_attempt_at <= now 的任务
      ORDER BY next_attempt_at, id
      LIMIT 1
      FOR UPDATE SKIP LOCKED
  → 没有候选行：Optional.empty()
  → 有候选行：同一事务内 UPDATE 为 RUNNING
  → 递增 attempt_count，写入租约与 started_at
  → 提交事务并返回任务摘要
```

- **改动边界**：修改 `CaptureJobMapper` 与 `CaptureJobService`；不建表、不改迁移、不加 Controller、不启动定时 Worker。
- **为什么放这层**：锁与条件更新属于任务领域；放 Worker 调度器里，未来手动重新采集或测试 Worker 会复制一套抢占规则。

#### 5. 重难语法讲解

- **多行原生 SQL**
  - 标准写法：MyBatis 方法上使用 `@Select` 或 `@Update`，每个参数用 `@Param("name")` 命名。
  - 关键点：`FOR UPDATE SKIP LOCKED` 必须是锁定查询的一部分；参数 `now` 让测试和业务都使用注入 `Clock` 计算出的时间。
  - 常见错法：把 `LIMIT` 写到 `FOR UPDATE` 后面，MySQL 语法会失败。
- **`Optional<CaptureJobSummary>`**
  - 标准写法：没有待办任务时返回 `Optional.empty()`；有任务时返回 `Optional.of(summary)`。
  - 关键点：队列为空是正常业务状态，不是 404。
  - 常见错法：返回 `null` 让调用方漏掉空值分支，或在无任务时抛异常制造无意义错误日志。

#### 6. 具体实现

本节是实现契约；生产代码由用户按契约完成，Codex 补充真实数据库测试。

##### `backend/src/main/java/com/webcollector/capture/mapper/CaptureJobMapper.java`
- **作用**：选出下一条可领取任务，并在同一事务里把选中行迁移为 `RUNNING`。
- **建议签名**：
  - `Long selectNextClaimableJobId(LocalDateTime now)`
  - `int claimPendingJob(Long jobId, String workerId, LocalDateTime now, LocalDateTime lockedUntil)`
- **查询契约**：筛选 `status='PENDING'` 且 `next_attempt_at <= now`，按 `next_attempt_at, id` 升序，取一条并加 `FOR UPDATE SKIP LOCKED`。
- **更新契约**：`WHERE id=? AND status='PENDING'`；设置 `status='RUNNING'`、`attempt_count=attempt_count+1`、`locked_by`、`locked_until`、`started_at`、`updated_at`。不写 `finished_at` 和错误字段。
- **怎么验证**：在真实 MySQL 中执行候选查询，确认索引和行锁行为；查询无候选任务时返回 `null`。

##### `backend/src/main/java/com/webcollector/capture/service/CaptureJobService.java`
- **作用**：定义一次短事务内的领取用例，并校验 Worker 与租约参数。
- **建议签名**：`Optional<CaptureJobSummary> claimNext(String workerId, LocalDateTime lockedUntil)`。
- **事务契约**：方法标 `@Transactional`；候选查询、条件更新和回读必须在同一个事务内。
- **参数契约**：`workerId` 非空白且长度不超过 100；`lockedUntil` 截断到毫秒后必须严格晚于当前时间。
- **复用契约**：现有 `claim(jobId, workerId, lockedUntil)` 与新方法共用同一个条件更新和摘要映射逻辑，也递增 `attempt_count`。

##### 测试文件
- **作用**：证明索引选择、空队列、并发领取和 `SKIP LOCKED` 行为。
- **至少覆盖**：到期任务排序、未来任务不可领、空闲返回空、两 Worker 争一条、两 Worker 领两条、人工锁住唯一任务时快速返回空、释放后可领取。

#### 7. 计算机四大件映射

- **映射到**：操作系统。
- **具体机制**：数据库行锁对应临界区保护；`SKIP LOCKED` 对应“拿不到锁就跳过”，避免所有线程阻塞在同一资源上。
- **在哪一行代码体现**：Mapper 候选查询的 `FOR UPDATE SKIP LOCKED`，以及 Service 上覆盖查询与更新的 `@Transactional`。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ 查询和更新各开一个事务 → 查询提交后行锁提前释放 → 另一个 Worker 能再次选中同一行；改为同一个 `@Transactional`。
- ❌ 只写 `FOR UPDATE` 不写 `SKIP LOCKED` → 第二个 Worker 一直等待第一行 → 增加 `SKIP LOCKED`，让查询继续寻找其他候选。
- ❌ 更新时只按 `id` 不校验 `status='PENDING'` → 状态可能被无条件覆盖 → 条件更新保留状态保护。
- ❌ 把这步扩成定时 Worker 或失败重试 → 混入 M3.3/M3.4 范围 → 本轮只提供可测试的领取方法。

**能讲（Codex 先示范，用户随后合上材料作答）**
- [ ] Q1：为什么候选查询和状态更新必须放在同一个事务里？

  > **参考示范**：`SELECT ... FOR UPDATE` 锁住的是事务内的行。如果查询提交后再更新，锁已经提前释放，其他 Worker 可能也选中同一行；放在同一事务里，行会一直锁到 `RUNNING` 已写入并提交，另一 Worker 只会跳过它。更新仍保留 `status='PENDING'` 条件，是第二道保护。

- [ ] Q2：`SKIP LOCKED` 解决的是锁等待还是重复消费？

  > **参考示范**：它主要解决锁等待：已被其他事务锁住的行不再排队等待，而是跳过去找下一条。防止同一条任务被成功消费两次，靠的是短事务中的行锁、状态迁移和条件更新三者配合，不能只说成 `SKIP LOCKED` 单独完成的。
