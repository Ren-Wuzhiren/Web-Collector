# 二级阶段 M5.2：让写入与读取都安全、删除也一致

**一句话**：把快照安全登记和授权读取接起来；删除数据库资产后，文件清理失败仍可重试。
**完成标志**：资产按所属用户授权读取；资产或链接删除先持久化清理任务，再删除数据库记录；清理器可并发领取、恢复过期租约并持续退避重试。

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| Java NIO `Files` | 暂存、原子提升、读取和删除资产 | 同根目录原子移动，不增加基础设施 | 对象存储留到多机部署再评估 |
| Spring 事务与事务同步 | asset/cleanup 记录及文件补偿 | DB 事务不能回滚磁盘，回滚后显式恢复/入队 | 不假设存在跨资源 XA |
| MySQL + `FOR UPDATE SKIP LOCKED` | 持久化清理队列与并发领取 | 复用项目数据库队列模式；多实例不重复领取 | 不引入 Redis 队列，需持久化错误重试 |
| Spring Scheduling | API 进程周期消费清理队列 | 单机部署无需独立 Worker 服务 | 独立进程留给后续部署演进 |

#### 2. 原理讲解（不用它会怎样）

- **原子文件可见性**：完整写入临时文件后原子移动；不支持原子移动就失败，不把部分文件作为正式资产暴露。
- **DB/文件系统不是一个事务**：删除记录与清理路径在同一 DB 事务；文件删除异步执行并可重试。若把文件操作包在 `@Transactional` 里当作可回滚，DB 回滚不会恢复已经移动或删除的文件。
- **租约 + 幂等删除**：领取时写入过期时间；进程崩溃后租约到期即可再领。目标文件不存在视为成功，避免“删文件后、删队列记录前崩溃”导致任务卡死。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：Controller → AssetService / LinkService → AssetMapper 与 AssetCleanupService → MySQL；AssetCleanupWorker 调用 AssetStorage 操作本地文件。
- **数据流向**：快照暂存文件 → 根目录校验 → 原子移动到 UUID 路径 → 写 asset 元数据；删除资产/链接 → 同事务入清理队列并删除 DB 行 → 定时领取 → 删除文件 → 删除队列记录。
- **改动边界**：新增 V12 `asset_cleanup_job`；存储根配置统一为 `app.storage.root`。清理队列表不引用 asset/link/job 外键，避免父记录级联时队列一并消失。
- **安全边界**：读取用 `asset id + link.user_id` 联查；路径按根目录规范化并校验真实父路径；HTML 以附件返回并设置 `nosniff`。

#### 5. 重难语法讲解

- **`Files.move(..., ATOMIC_MOVE)`**：只在同一文件系统支持时执行原子提升；不能用它作为 `Files.copy` 的选项，也不静默降级。
- **`@Transactional(propagation = REQUIRES_NEW)`**：仅用于主事务回滚后的文件补偿失败时独立写入清理任务；正常删除入队必须加入资产/链接删除事务。
- **`FOR UPDATE SKIP LOCKED`**：候选任务行在短事务内加锁并写租约；文件 IO 在提交后进行，不能持锁等待磁盘操作。

#### 6. 具体实现

##### `backend/src/main/java/com/webcollector/capture/asset/storage/AssetStorage.java`
- **作用**：在唯一 `app.storage.root` 下完成临时写入、SHA-256、原子移动、提升/恢复、授权路径解析和删除。
- **关键边界**：数据库登记提交失败时将提升后的文件恢复到原暂存路径；恢复失败则尝试通过独立事务持久化清理任务。
- **怎么验证**：`AssetStorageTest` 覆盖哈希、原子移动不支持、源流中断、路径穿越和符号链接逃逸。

##### `backend/src/main/java/com/webcollector/capture/asset/service/AssetCleanupService.java`
- **作用**：在资产/链接删除事务中入队；短事务领取一个任务并写两分钟租约。
- **失败策略**：文件不存在按成功处理；其他失败保存错误并以 5 秒起步、最长 6 小时的指数退避持续重试。
- **怎么验证**：Testcontainers 覆盖链接级联后队列留存、事务回滚、并发唯一领取、租约恢复和失败重试。

##### `backend/src/main/java/com/webcollector/capture/asset/controller/AssetController.java`
- **作用**：`GET /api/v1/assets/{id}` 文件流读取与 `DELETE /api/v1/assets/{id}` 异步删除。
- **响应**：读取返回实际 MIME、长度和 `X-Content-Type-Options: nosniff`；HTML 固定附件名；删除返回 `202`。
- **怎么验证**：`AssetControllerTest` 覆盖当前用户 ID、404、HTML 附件头及 202。

#### 7. 计算机四大件映射

- **映射到**：操作系统 / 文件系统。
- **具体机制**：同一文件系统上的原子重命名提供目录项可见性切换；跨数据库与文件系统没有共同 ACID 事务，因此采用补偿与持久化清理队列。
- **在哪一行代码体现**：`AssetStorage.moveAtomically`；`AssetRegistrationService` 的事务完成回调。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ `Files.copy` 使用 `ATOMIC_MOVE` → 复制 API 不接受移动选项 → 写临时文件后用 `Files.move` 原子提升。
- ❌ 删除链接后再查询资产路径 → 外键级联已删 asset 行 → 必须在删除链接前、同一事务登记路径。
- ❌ 清理任务引用 asset 外键 → asset 删除时队列一起级联 → 清理任务只保存路径，不设父表外键。
- ❌ 直接用客户端或 DB 路径拼磁盘绝对路径 → 可能越过根目录 → 只解析根目录相对 key 并检查规范化/真实父路径。
