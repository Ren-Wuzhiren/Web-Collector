### 二级阶段 M3.1：让任务能排队、认领、收尾

**一句话**：给 `capture_job` 装上状态机，让任务能按规则从 `PENDING` 走到终态。
**完成标志**：一条任务能走完 `PENDING → RUNNING → SUCCEEDED`；非法跳转被拒绝且数据库状态不变。
**预计时长**：4 件　**依赖**：M2.6 已完成

---

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| Spring `@Transactional` | 每次状态迁移一个短事务 | 迁移要么生效要么不生效 | 把整个采集过程包进一个事务 → 数据库连接被占用几十秒 |
| MyBatis-Plus `LambdaUpdateWrapper` | 条件更新（`WHERE id=? AND status=?`） | 一条 SQL 同时完成“判断 + 修改”，受影响行数就是判断结果 | 先 `selectById` 再 `updateById`，两步之间有窗口 |
| MySQL 8 状态列 | 承载状态与租约字段 | 已在 V9 落地，`idx_job_claim` 已就位 | 引入内存状态机 → 重启即丢 |

#### 2. 原理讲解（不用它会怎样）

- **状态机**：允许的迁移是一张白名单，不在这张表里的跳转一律拒绝。不用它：`FAILED` 的任务能被改回 `RUNNING`，或者已成功的任务被再次领取，最后没人说得清这条任务到底跑没跑完。
- **条件更新（CAS）**：`UPDATE ... WHERE id=? AND status='PENDING'`，受影响行数为 1 才算成功。不用它：先查再改，两个调用方都能查到 `PENDING` 并都通过检查，同一条任务被认领两次。
- **短事务**：认领和收尾各开一个事务，中间“真正去抓网页”的部分不在事务里。不用它：事务从认领一直开到采集结束，连接被一个慢网页占住，并发一高就耗尽连接池。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：`（调用方 / 未来的 Worker）→ CaptureJobService → CaptureJobMapper → MySQL`。
- **数据流向**：

```text
claim(jobId, workerId, lockedUntil)
  → UPDATE capture_job
       SET status='RUNNING', locked_by=?, locked_until=?, started_at=?
     WHERE id=? AND status='PENDING'
  → 影响 1 行：返回摘要；影响 0 行：再查一次，区分 404 与 409
```

- **改动边界**：只动 `capture` 包与 `ErrorCode`；不加 Controller、不碰 `LinkService`、不做重试。
- **为什么放这层**：状态规则属于任务领域。放 Worker 里，将来第二个调用方（手动重采集）要复制一遍；放 Mapper 里，SQL 就要写业务判断。

#### 4. 步骤（每步都能看到结果）

#### 5. 重难语法讲解

- **`LambdaUpdateWrapper` 的条件更新**
  - 标准写法：`.eq(CaptureJob::getId, id).eq(CaptureJob::getStatus, PENDING).set(CaptureJob::getStatus, RUNNING)`，再 `captureJobMapper.update(null, wrapper)`。
  - 参数含义：第一个参数传 `null` 表示不基于实体更新，只走 wrapper 的 `set`；返回值是受影响行数。
  - 常见错法：传一个新建的实体进去 → 框架按实体非空字段拼 SET，没赋值的列会被覆盖成 null。
- **枚举上的迁移判断**
  - 标准写法：`canTransitionTo(target)` 内部用 `switch (this)` 返回允许的目标集合。
  - 参数含义：`this` 是当前状态，`target` 是想去的状态，返回是否允许。
  - 常见错法：把判断散在 Service 的多个 if 里 → 新增状态时漏改一处，规则就分叉。

#### 6. 具体实现

> 本轮由用户手写生产代码，Codex 编写测试；本节只给契约，不给完整实现。

##### `backend/src/main/java/com/webcollector/capture/entity/CaptureJobStatus.java`
- **作用**：集中定义四条状态与迁移白名单。
- **契约**：`canTransitionTo` 只放行 `PENDING→RUNNING`、`RUNNING→SUCCEEDED`、`RUNNING→FAILED`；null、原地迁移与终态回退一律 false。

##### `backend/src/main/java/com/webcollector/common/web/ErrorCode.java`
- **作用**：给非法迁移一个稳定错误码。
- **契约**：`CAPTURE_JOB_INVALID_STATE(409, "任务状态不允许该操作")`。

##### `backend/src/main/java/com/webcollector/capture/service/CaptureJobService.java`
- **作用**：承载认领与收尾的状态迁移。
- **契约**：
  - `CaptureJobSummary claim(Long jobId, String workerId, LocalDateTime lockedUntil)`
  - `CaptureJobSummary complete(Long jobId)`
  - `CaptureJobSummary fail(Long jobId, String errorCode, String errorMessage)`
  - 三个方法都用条件 UPDATE；受影响行数为 0 时再查一次，区分“任务不存在”（404）与“状态不对”（409）。
  - 收尾时清空 `locked_by` / `locked_until`，写入 `finished_at`。
- **事务边界**：三个方法各开一个短事务，默认 `REQUIRED`。

##### 测试
- **作用**：证明迁移白名单和条件更新在真实数据库上成立。
- **覆盖**：`CaptureJobStatusTest` 的迁移真值表；`CaptureJobServiceTest` 的认领、完成、失败、二次认领被拒、跳过认领被拒、终态重复收尾被拒、任务不存在。

#### 7. 计算机四大件映射

- **映射到**：本步不强行映射到四大件。
- 条件更新背后的行锁与 `SKIP LOCKED` 才是操作系统并发的真实素材，那在 `M3.2`，届时再讲临界区、锁等待与跳过已锁行。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ 先 `selectById` 再判断状态 → 并发窗口里两个调用方都通过 → 条件 UPDATE + 受影响行数。
- ❌ `updateById` 传整个实体 → 没加载的 `locked_by` 被写成 null → 只用 wrapper 的 `set` 指定列。
- ❌ 收尾不清理 `locked_*` → M3.3 的恢复扫描把已完成任务当成“锁过期” → 收尾时清空。
- ❌ 在 `fail` 里顺手做重试 → 把 M3.3 的指数退避混进来 → 本轮 `fail` 直接进终态。

**能讲（必须自己回答，不许看前面）**
- [x] Q1：为什么用“条件 UPDATE + 受影响行数”，而不是“先查再改”？

  > 我的回答：先查后改，同一个任务被认了两次，UPDATE会给SQL加排他锁，受影响行数直接告诉你要么可以运行，要么被抢了，要么根本不存在。

- [x] Q2：`fail` 之后如果不清 `locked_until`，M3.3 的恢复扫描会误判成什么？

  > 我的回答：不及时清理，那就会陷入反复失败，反复执行的恶性循环，看到FAILED任务，存在的干扰项会加大排查难度
