### 二级阶段 M9.1：用三十个真实网页证明它好用

**一句话**：用固定数据集在真实 Compose 栈上保存 30 个 URL，得到可复现的成功率、耗时和失败边界成绩单。
**完成标志**：一次性账号跑完 26 个正向和 4 个负向案例；正向成功率不低于 90%，成功案例中位耗时不超过 30 秒，负向案例均符合预期。
**预计时长**：4–6 小时（含真实网页抓取等待）　**依赖**：M8 验收完成

---

#### 1. 涉及技术栈（为什么是它）

| 技术/组件 | 用在哪 | 为什么选它 | 备选 & 不选的理由 |
|---|---|---|---|
| PowerShell 7 | 顺序调用现有 HTTP API 并轮询任务 | 现有验收脚本和 Windows 环境已经使用它 | 改用 Node 会新增一套运行入口，没有额外验收收益 |
| Node `node:test` | 数据集契约与脚本行为测试 | 仓库已有脚本测试模式，无需新增依赖 | JUnit 只测试 Java 边界，不能直接驱动 PowerShell 脚本 |
| Docker Compose | 提供真实 MySQL、Redis、后端和 Nginx | M8 已验证同形态栈，M9 应复用真实运行路径 | 本地进程混合启动无法证明容器链路 |
| JSON | 固定数据集和保存逐项证据 | 可版本化、可机读、便于汇总 | 纯文本 URL 无法表达预期成功或失败 |

#### 2. 原理讲解（不用它会怎样）

- **【预期结果与实测结果分离】**：数据集先声明每个 URL 应成功还是失败，运行后再比较。全部只按 `SUCCEEDED` 统计时，超时和 SSRF 边界会被误算成业务失败，成功率失去意义。
- **【硬超时】**：轮询必须在截止时间结束，不能无限等待。缺少它时，一个卡在 `PENDING` 的任务会让整份验收永远不返回。
- **【资产可读校验】**：任务终态成功只证明数据库登记完成。缺少回读时，数据库有记录但文件已丢失仍会被误判为可回看。

#### 3. 架构讲解（这一步在整体里占哪个位置）

- **分层位置**：验收脚本 → Nginx → Controller → Service → MySQL/Redis → Capture Worker → 文件存储；脚本不直接访问数据库或容器文件。
- **数据流向**：读取 JSON 数据集 → 创建一次性账号 → 逐项 `POST /links` → 轮询 `/jobs/{id}` → 读取首个资产 → 比较预期 → 输出 JSON 和退出码。
- **改动边界**：新增脚本数据集、脚本测试、验收脚本、阶段卡和验收单；不碰后端生产类、表结构、迁移和已运行数据卷。
- **为什么放这层**：通过公开 HTTP 契约验收，才能覆盖鉴权、限流、任务调度和资产授权；直接读数据库会绕过真实用户路径。

#### 4. 步骤（每步都能看到结果）

| # | 做什么 | 完成后能观察到什么 |
|---|---|---|
| 1 | 校验 30 条固定数据集 | 26 正向、4 负向，ID/URL 唯一且类别完整 |
| 2 | 启动一次验收会话 | 自动注册唯一账号并取得默认 Inbox |
| 3 | 顺序提交并轮询每个 URL | 每项输出终态、错误、耗时和资产格式 |
| 4 | 回读首个资产并比较预期 | 每项得到 `matched=true/false` |
| 5 | 汇总全量结果 | 成功率、中位耗时、三格式率和负向分布可见 |

#### 5. 重难语法讲解

- **【PowerShell `ConvertFrom-Json`】**：`$data = Get-Content -Raw $path | ConvertFrom-Json`；`-Raw` 是让中文 JSON 一次解析的关键，省略后可能逐行产生字符串而不是对象。
- **【PowerShell `Retry-After`】**：429 响应头单位是秒；脚本读取正整数并等待后再试。常见错法是固定重试，容易在窗口未结束时连续撞限流。
- **【Node `spawn`】**：测试用独立子进程执行 `.ps1`，断言真实退出码和输出；直接调用脚本源码文本无法证明脚本行为。

#### 6. 具体实现

##### `scripts/acceptance/m9-real-urls.json`

- **作用**：冻结 30 条 URL、类别和预期终态。
- **关键结构**：

```json
{
  "schemaVersion": 1,
  "cases": [
    {
      "id": "general-01",
      "category": "baseline",
      "url": "https://example.com",
      "expectedOutcome": "CAPTURE_SUCCEEDED"
    }
  ]
}
```

- **怎么验证**：脚本测试断言总数、正向数、负向数、唯一性和必需类别。

##### `scripts/accept-real-urls.ps1`

- **作用**：执行真实 URL 验收并生成不入库的 JSON 证据。
- **接口**：

```powershell
.\scripts\accept-real-urls.ps1 `
  -BaseUrl http://127.0.0.1:18080 `
  -DatasetFile .\scripts\acceptance\m9-real-urls.json `
  -OutputFile .\data\acceptance\m9\results.json `
  -JobTimeoutSeconds 300 `
  -PollIntervalSeconds 3
```

- **可选子集**：`-CaseId failure-timeout,failure-redirect,failure-size,failure-ssrf` 仍完整校验 30 条数据集，但只执行指定案例；报告写入 `scope=SELECTED` 和 `selectedCaseIds`。
- **关键契约**：顺序执行；一次性随机账号；任务硬超时；429 按 `Retry-After` 重试；成功项至少一个资产可读取；报告不含密码和 token。
- **怎么验证**：`node --test .\scripts\tests\accept-real-urls.test.mjs`。

##### `docs/需求文档/2026-11-08-032-M9.1-三十个真实URL验收单.md`

- **作用**：记录运行环境、逐项结果、指标、失败分布和未验证项。
- **怎么验证**：每个门槛与 JSON 汇总一致，不能只写“测试通过”。

#### 7. 计算机四大件映射

- **映射到**：计算机网络
- **具体机制**：HTTP 状态码、`Retry-After`、请求/连接超时和重定向上限。
- **在哪一行代码体现**：429 重试分支、`Invoke-WebRequest -TimeoutSec` 和任务轮询截止时间。

#### 8. 坑（会怎么错，不是要注意什么）

- ❌ 只统计所有 URL 的 `SUCCEEDED` 数量 → 预期失败的边界被算成产品缺陷 → 分别统计正向成功率和预期匹配率。
- ❌ 成功任务只检查 `assets.Count` → 文件丢失仍通过 → 至少读取一个资产并要求 HTTP 200、非空内容。
- ❌ 固定账号重复运行 → 第二次开始全部 409 → 每次生成唯一的一次性账号。
- ❌ 把密码、token 或 Authorization 写进报告 → 验收证据泄漏凭据 → 任何日志和 JSON 都不包含这些值。
