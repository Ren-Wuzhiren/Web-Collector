# 项目开发工作流（13 步 + 二级阶段拆解）

本技能是 `AGENTS.md` 的展开版。冲突时以 `AGENTS.md` 的契约和语气为准，以本文件的方法论为准。

---

## 一、开工：三轮协商

不做完协商不许写代码。

### R1 提案（你输出）

```
## 我理解的项目
{一句话}。使用者是 {谁}，痛点是 {什么}。

## 一期范围（建议）
{3–6 条}

## 不做（建议砍掉）
{至少 3 条 + 为什么现在不做}

## 一级阶段划分
G1 立项 → 产出 {…}
G2 方案 → 产出 {…}
...
每个 G 给一句"做完这个阶段你能对外说什么"。

## 两个关键取舍
1. {选 A 不选 B}，因为 {…}，代价是 {…}
2. {…}

## 我需要你回答的 3 个问题
1. {会改变方案的问题}
```

### R2 修订

用户提意见后，**先指出他改动里的问题**，再改。不要无条件顺从。

### R3 冻结

写 `docs/ROADMAP.md`：

```markdown
# 路线图
## 一期目标
## 不做什么
## 阶段表
| 阶段 | 二级阶段 | 产出 | 状态 |
|---|---|---|---|
| G1 | 1-1 用户访谈提纲 | docs/01-brief.md | ☐ |
```

## 二、13 步各自的动作与验收

### 1 用户对接
- 动作：问 5 件事——谁用、什么场景、现在怎么凑合解决、最痛的一点、什么情况下算"没它不行"。
- 产出：`docs/01-brief.md`，含"一句话价值"和"3 个真实使用场景"。
- 验收：能说出目标用户的**具体身份**（不是"广大用户"）。
- 坑：跳过这步直接写功能，最后做出来没人用。

### 2 需求文档
- 动作：用户故事（As a / I want / So that）+ 功能清单（MoSCoW 分级）+ 非功能需求（性能、安全、兼容）+ 不做清单。
- 产出：`docs/02-prd.md`。
- 验收：每条需求可判定"做了没有"，不存在"体验更好"这种不可测条目。
- 坑：把技术方案写进需求（"用 Redis 做缓存"是方案不是需求）。

### 3 原型
- 动作：页面清单 → 每页的信息层级 → 主交互路径。文字或 ASCII 线框即可，不上 Figma。
- 产出：`docs/03-wireframe.md`。
- 验收：闭着眼睛能走完"注册→登录→发文章→看文章"。
- 坑：先画美化再想结构。

### 4 可行性
- 动作：技术风险（不会的技术点列出来）、时间风险（按 2 倍估）、能力风险（哪些必须现学）。
- 产出：`docs/04-feasibility.md`，每条风险配一个降级方案。
- 验收：至少 3 条风险 + 3 条降级。
- 坑：只写"可行"两个字。

### 5 流程图
- 动作：Mermaid 画主流程 + 至少 2 条异常流程（失败、超时、重复提交）。
- 产出：`docs/05-flow.md`。
- 验收：异常分支有明确处理动作。
- 坑：只画 happy path。

### 6 技术选型
- 动作：每个组件写"选它 / 备选 / 为什么不选备选 / 版本号"。
- 产出：`docs/06-stack.md`。
- 验收：每个选择都有"不用它会怎样"。
- 坑：为了简历堆技术。**单人项目，能少一个组件就少一个。**

### 7 架构
- 动作：分层图、模块边界、一次请求的完整调用链（从浏览器到数据库再回来）、部署形态。
- 产出：`docs/07-arch.md`。
- 验收：能画出"一个请求经过哪些类"，并说明每层职责。
- 坑：过早抽象（上来就搞 DDD 四层 + 领域事件）。

### 8 数据库设计
- 动作：ER 图 → 建表 SQL（含类型、长度、默认值、注释）→ 索引及理由 → 至少 3 条典型查询。
- 产出：`docs/08-db.md` + `sql/schema.sql`。
- 验收：每个字段的类型能说出理由（为什么 `VARCHAR(64)` 不是 `TEXT`）。
- 坑：不建索引 / 全建索引；`utf8` 而非 `utf8mb4`；时间用字符串存。

### 9 接口文档
- 动作：路径、方法、鉴权、入参、出参、错误码、示例。
- 产出：`docs/09-api.md`。
- 验收：照着文档能用 curl 打通。
- 坑：只写成功响应，不写错误码。

### 10 编码
- 动作：按二级阶段推进，每阶段一张卡，格式严格按 `docs/STAGE-TEMPLATE.md`（源头是 `templates/stage-card.md`）。
- 验收：每阶段结束能运行 + 能讲清 2 个问题。
- 坑：一口气写十个文件再一起调试。

### 11 审核
- 动作：按四个维度过一遍——安全（SQL 注入、越权、明文密码）、性能（N+1 查询、缺索引、大事务）、可读（命名、重复）、边界（空值、超长、并发）。
- 产出：`docs/11-review.md`，分"必须改 / 建议改 / 记录不改"。
- 验收：每类至少查 1 条。

### 12 部署
- 动作：打包 → 环境变量清单 → 启动命令 → 健康检查 → 回滚步骤 → 日志位置。
- 产出：`docs/12-deploy.md` + `Dockerfile`/脚本。
- 验收：换一台干净机器能照文档跑起来。

### 13 验收交付
- 动作：逐条对 PRD 打勾 → 列已知问题 → 写"下一步三个方向" → 写一份"我学到了什么"。
- 产出：`docs/13-accept.md`。
- 验收：README 能让陌生人跑起来。

## 三、二级阶段怎么切

**切法**：按"可独立验收的行为"切，不按"技术层"切。

- ❌ 按层切：先写所有 Entity，再写所有 Service（每层都无法单独验收）
- ✅ 按行为切：注册能用 → 登录能用 → 发文章能用 → 文章列表分页能用

**颗粒度判据**（满足 3 条即可开工）：
1. 一次会话（2–4h）能写完。
2. 写完能跑出一个可观察的结果。
3. 不需要同时改 3 个以上模块。

**每个二级阶段的依赖要显式写**：`依赖：?-? 完成`。

## 四、讲解的写法（关键）

用户是"能看懂但写不出、会背名词但讲不透"的状态。所以每个概念按这个顺序讲：

1. **它是什么**（一句话，不含术语）
2. **它解决什么问题**（反例：没有它会出什么事）
3. **它怎么做到的**（机制，配一张文字图）
4. **在代码里长什么样**（贴 5–15 行，逐行注释"为什么"）
5. **它什么时候不该用**（边界）
6. **检验**（一个必须自己回答的问题）

**四大件映射表**（挑最贴切的一条，不要硬凑四条）：

| 代码现象 | 底层知识 | 该讲的机制 |
|---|---|---|
| 线程池配置 | 操作系统 | 线程切换成本、上下文、阻塞/非阻塞 |
| 连接池、超时重试 | 计算机网络 | TCP 三次握手、TIME_WAIT、滑动窗口、队头阻塞 |
| 索引、分页深翻 | 数据结构 | B+ 树高度、回表、覆盖索引、复杂度 |
| 缓存行、整数溢出、字符编码 | 计算机组成 | 存储层次、二进制表示、UTF-8 变长编码 |
| 锁、CAS、内存可见性 | 操作系统 + 组成 | 原子指令、内存屏障、缓存一致性 |

## 五、常见失败模式（自查）

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 二级阶段越做越大 | 没有"可观察产出"的定义 | 回到"一句话说清做完能看见什么" |
| 代码能跑但讲不出 | 跳过了第 3–5 步讲解 | 停下来补原理，不加新代码 |
| 每个阶段都在改前面的代码 | 设计阶段（G3）没过 | 回去补架构和表设计，别硬扛 |
| 项目做到一半没兴趣 | 一期范围太大 | 砍到"两周能演示"的版本 |
| AI 给的代码风格前后不一致 | 没有 `PROJECT.md` 约定 | 先固化约定再写代码 |
