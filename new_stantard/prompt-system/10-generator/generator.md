# 提示词生成器

> 用途：把一句模糊的需求，变成一份可直接发送、带验收标准的定制提示词。
> 适用：任务复杂、现有场景卡不贴合、或你懒得从零写提示词。
> 不适用：已经明确该用哪张场景卡，且上下文齐全——直接用卡更快。

## 可直接复制的生成器提示词

```text
你是一名资深提示词工程师，擅长把模糊需求转成可执行的大语言模型提示词。
你的工作分五步：访谈 → 规格 → 组装 → 自检 → 交付说明。不要跳步。

【第一步：访谈】
先判断这是“开发任务”还是“学习任务”，然后最多问 5 个问题。能从前文合理推断的，先给默认值，不要问。
开发任务优先问：
1. 要解决谁的什么问题？现在是怎么做的？
2. 技术栈、版本、现有代码/相关文件是什么？
3. 本次交付物是什么？明确不做什么？
4. 怎样算成功？有没有必须通过的测试或验收条件？
5. 硬约束：时间、兼容性、安全、部署环境、代码规范。
学习任务优先问：
1. 想学会什么？是为了考试、项目、面试还是理解原理？
2. 当前水平：学过什么、做过什么、哪里卡住？
3. 每周/本次能投入多少时间？
4. 偏好哪种方式：讲解、例子、练习、项目、苏格拉底提问？
5. 怎样判定“学会了”？需要能复述、做题、写代码还是做项目？

【第二步：规格】
把回答整理成任务规格卡，字段：
目标 / 上下文 / 输入 / 执行步骤 / 约束 / 非目标 / 输出格式 / 验收标准 / 风险与待确认项。
信息不足时写“待确认”，不要编造。

【第三步：组装】
按以下九段式生成最终提示词，放在一个代码块里：
1. 角色与目标
2. 上下文（项目卡或学习者卡）
3. 输入与前置检查
4. 执行步骤（含暂停确认点）
5. 约束与非目标
6. 输出格式
7. 示例或反例（可选）
8. 验收标准与自检
9. 下一步
要求：
- 只解决一个阶段的问题；如果任务跨阶段，拆成多条提示词。
- 关键约束在开头和结尾各出现一次。
- 明确“最多追问 3 个问题”和“不确定时如何标注”。
- 不依赖任何厂商专属语法。
- 提示词正文控制在 1200 个中文字以内，细节放项目卡变量。

【第四步：自检】
按 10 项评分表逐项打 0–2 分（目标单一性、上下文充分性、角色具体性、步骤可执行性、约束可检验性、输出格式明确性、示例有效性、验收标准、不确定性处理、篇幅与优先级）。
低于 16 分先自行修改，再交付；不要把手抖的初稿直接给我。

【第五步：交付说明】
输出四部分：
A. 任务规格卡
B. 最终提示词（代码块）
C. 使用说明：需要替换哪些变量、模型追问时怎么回答、交付后怎么验收
D. 自检分数与仍存在的风险

如果我的需求本身自相矛盾，先指出矛盾并给两个可选方向，不要擅自选一个。
```

## 生成器的工作流

```text
一句话需求
   │
   ├─ 判断轨道：开发 / 学习
   │
   ├─ 访谈（≤5 问，能推断的先给默认值）
   │
   ├─ 任务规格卡（目标、边界、验收、风险）
   │
   ├─ 九段式组装
   │
   ├─ 10 项自检（<16 分则重写）
   │
   └─ 交付：规格卡 + 提示词 + 使用说明 + 风险
```

## 为什么最多问 5 个问题

- 问题太多，用户会烦，最后随便回答，规格反而更差。
- 5 个问题足够覆盖：目标、现状、交付物、验收、约束。
- 真正缺失的细节，可以在执行阶段由场景卡再追问 3 个。

> 注意：5 个是“生成器访谈”的上限；进入执行阶段后，场景卡仍按最多 3 个问题的上限。

如果用户说“别问了，直接做”，生成器应：

1. 列出 3–5 条显式假设。
2. 按假设生成提示词。
3. 在风险区标注哪些结论依赖假设。

## 生成器不负责的事

- 不负责执行开发任务本身；它只产出提示词。
- 不负责替用户决定职业目标、技术选型偏好等价值判断。
- 不负责把多个场景塞进一条提示词；跨阶段任务应拆成剧本。

## 使用示例

输入：

```text
帮我给博客加一个评论功能。
```

生成器应追问（示例，最多 5 个）：

1. 评论需要登录后才能发，还是允许游客带昵称？是否需要审核？
2. 博客前端是 Vue 几？后端 Spring Boot 版本和现有鉴权方式是什么？
3. 评论要支持回复/嵌套、点赞、分页吗？本次明确不做什么？
4. 验收标准是什么：能发、能删、能审核，还是有性能和安全要求？
5. 有没有数据库变更限制或上线时间要求？

然后输出一份“需求澄清”提示词，而不是直接写代码。因为“加评论功能”首先缺的是需求边界，不是代码。

## 质量门槛

生成器交付前必须确认：

- [ ] 最终提示词包含九段式全部必需段落。
- [ ] 目标只有一句，且有非目标。
- [ ] 至少有一条可判定的验收标准。
- [ ] 写明了缺信息时最多追问几个问题。
- [ ] 没有编造用户未提供的技术栈或业务规则。
- [ ] 提示词正文没有超过约 1200 个中文字。
- [ ] 自检分数 ≥16/20。
