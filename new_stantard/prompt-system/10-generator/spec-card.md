# 任务规格卡

> 用途：在写提示词之前，先把“要做什么”钉死。规格卡是生成器的中间产物，也是验收依据。
> 原则：一卡一任务；写不清的字段标“待确认”，不要用漂亮话糊过去。

## 填写示例：博客评论功能（开发）

```markdown
# 任务规格卡

## 基本信息
- 任务名称：博客评论功能（第一版）
- 轨道：开发
- 版本：v0.1
- 日期：2026-10-18

## 目标
为博客读者提供“登录后可发表评论”的能力，交付后端接口 + 前端表单 + 数据库变更。

## 上下文
- 项目：个人博客（Spring Boot + Vue）
- 技术栈：Java 17、Spring Boot 3.x、MySQL 8、Vue 3（具体版本待确认）
- 相关文件：文章详情页、现有鉴权过滤器、评论相关表（待确认是否存在）
- 现有做法：读者只能阅读，无法互动

## 输入
- 已提供：功能一句话描述
- 需要补充：登录方式、是否审核、是否支持回复
- 缺失时：最多追问 3 个问题，其余按最小版本处理

## 执行步骤
1. 澄清评论的发布、删除、审核规则。
2. 设计表结构与接口。
3. 实现后端与前端。
4. 补测试并手动验证。
5. 暂停确认点：数据库结构变更前必须确认。

## 约束
- 硬约束：不改变现有文章接口；不引入新中间件。
- 软约束：沿用现有分层与异常处理。
- 安全：评论内容转义，防 XSS；接口需登录鉴权。

## 非目标
- 不做点赞、@提醒、富文本、图片上传。
- 不做游客评论。
- 不做评论搜索。

## 输出格式
- 表结构 SQL
- 接口清单（方法、路径、入参、出参）
- 后端与前端代码
- 测试用例与手动验证步骤

## 验收标准
- [ ] 登录用户能在文章下发表评论并立即看到。
- [ ] 未登录用户不能发表评论。
- [ ] 评论内容经过转义，脚本不会执行。
- [ ] 现有文章接口测试全部通过。
- [ ] 数据库变更可回滚。

## 风险与待确认
| 风险 | 影响 | 处理 |
|---|---|---|
| 现有鉴权方式不明 | 接口可能接错 | 先读 Security 配置 |
| 评论表可能已存在 | 重复建表 | 先查 schema |
| 前端状态管理方式不明 | 集成方式不同 | 先读文章详情页 |

## 建议使用的场景卡
`20-dev/01-requirements.md` → `20-dev/02-architecture.md` → `20-dev/03-implementation.md`
```

## 填写示例：TCP 三次握手（学习）

```markdown
# 任务规格卡

## 基本信息
- 任务名称：理解 TCP 三次握手
- 轨道：学习
- 版本：v0.1
- 日期：2026-10-18

## 目标
在不死记硬背的前提下，能用自己的话解释三次握手的必要性、状态变化和常见攻击面。

## 上下文
- 学习者：大二计算机专业，学过操作系统与 Linux，正在自学计算机网络
- 已学：C++、Java、Spring Boot、MySQL、Linux 基础
- 相关经验：做过 Spring Boot + Vue 博客，理解 HTTP 请求但未深入传输层

## 输入
- 已提供：主题与背景
- 需要补充：可用于学习的时间
- 缺失时：按单次 45 分钟设计

## 执行步骤
1. 用一个生活类比建立直觉。
2. 给出精确定义与状态变化。
3. 解释“为什么是三次而不是两次”。
4. 给一个反例/常见误解。
5. 出一道检查题，等我作答后再点评。

## 约束
- 不一次性倾倒全部 TCP 知识。
- 类比必须标注“类比到此为止”的边界。
- 我未作答前不给最终答案。

## 非目标
- 不展开拥塞控制、流量控制。
- 不要求背 RFC 原文。

## 输出格式
- 直觉
- 精确定义
- 状态变化表
- 常见误解
- 一道检查题

## 验收标准
- [ ] 我能不看资料画出三次握手时序。
- [ ] 我能解释两次握手为什么不够。
- [ ] 我能指出至少一个常见误解。

## 风险与待确认
| 风险 | 影响 | 处理 |
|---|---|---|
| 类比被当成精确定义 | 形成错误理解 | 类比后立即给定义与边界 |
| 内容过多 | 一次吸收不了 | 只讲握手，其余留到下一张卡 |

## 建议使用的场景卡
`30-learning/02-concept-tutor.md` → `30-learning/03-socratic-practice.md`
```

## 规格卡自检

- [ ] 目标能用一句话说清，且只有一个。
- [ ] 有明确的非目标。
- [ ] 验收标准可判定，不是“质量高”。
- [ ] 缺失信息有处理方式，不是留空。
- [ ] 风险区至少列出一条真实风险。
- [ ] 能据此选出 1–2 张场景卡，而不是十张。
