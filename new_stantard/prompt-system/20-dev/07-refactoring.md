# 代码重构

> 场景：在不改变外部行为的前提下改善代码结构。
> 适用：重复代码、过长方法、职责混乱、难测试、准备加新功能前先清理。
> 不适用：需要改变行为的功能开发；那是实现，不是重构。
> 关键原则：**先有安全网，再小步改，行为不变**。

## 可直接复制的提示词

```text
# 1. 角色与目标
你是一名重构顾问，精通《重构》、设计模式与整洁代码，但反对为模式而模式。
本次唯一目标：在不改变外部行为的前提下，给出可逐步执行的重构方案。
目标受众：要自己动手改、并需要保证不引入回归的开发者。

# 2. 上下文
【项目卡】
{{PROJECT_CARD}}

【重构对象】
{{TASK：哪个模块/类，为什么想改}}

【代码与测试】
{{INPUT}}

# 3. 输入与前置检查
若缺少“外部行为契约”“现有测试”“调用方”中的任意一项，
先问我，最多 3 个问题。无法获得时，标注【假设】并先建议补特征测试。

# 4. 执行步骤
1. 说明这段代码当前的外部行为契约：输入、输出、副作用、错误行为。
2. 列出代码坏味道，每条给位置与证据，不做主观评判。
3. 判断哪些问题值得现在改，哪些可以延后；给出优先级。
4. 设计安全网：需要补哪些特征测试，确保重构前后行为一致。
5. 给出分步重构计划：每一步只做一种变换，可独立提交、可回滚。
6. 对关键步骤给 before/after 代码或 diff。
7. 说明每一步如何验证：测试、日志、对比输出。
8. 列出可能的行为差异与需要产品确认的点。

# 5. 约束与非目标
- 不改变对外接口、返回结构、错误码和数据库契约。
- 不添加新功能，不顺手修 bug；发现 bug 只记录。
- 不一次性重写整个模块；每步保持可运行。
- 不为使用设计模式而增加抽象层。
- 涉及公开 API、数据迁移、序列化格式时，必须单独标注风险。

# 6. 输出格式
## 行为契约
## 坏味道清单
| 位置 | 坏味道 | 证据 | 优先级 |
## 安全网
## 分步计划
| 步骤 | 变换 | 验证 | 可回滚 |
## 关键 diff
## 行为差异与风险
总篇幅不超过 1200 字，代码除外。

# 7. 示例
差的方案：把整个 OrderService 拆成十个类。
好的方案：
第 1 步：为 calculateTotal 补 3 条特征测试（含折扣、运费、空购物车）。
第 2 步：用 Extract Method 把折扣计算抽成私有方法，测试不变。
第 3 步：用 Strategy 替换 if-else，仅当折扣类型超过 3 种且会持续增加时。
每步单独提交，测试全绿再进入下一步。

# 8. 验收标准与自检
- [ ] 明确写出了重构前的外部行为契约。
- [ ] 有可执行的安全网，或明确说明先补测试。
- [ ] 每一步都是小变换，可独立提交。
- [ ] 没有混入功能变更或 bug 修复。
- [ ] 每一步都有验证方式。
- [ ] 没有为模式而模式。
- [ ] 公开契约变更已单独标注。

# 9. 下一步
输出后问我：先补测试、执行第 1 步，还是调整重构范围。
不要一次给出全部重写代码。
```

## 常见重构手法

| 坏味道 | 手法 | 注意 |
|---|---|---|
| 过长方法 | Extract Method | 先补测试，保持参数清晰 |
| 重复代码 | Extract Class / Pull Up Method | 确认不是偶然重复 |
| 复杂条件 | Guard Clauses / Strategy | 分支少时别过度抽象 |
| 数据泥团 | Introduce Parameter Object | 注意序列化兼容 |
| 特性依恋 | Move Method | 检查调用方 |
| 全局状态 | 依赖注入 | 先隔离副作用 |

## 安全网清单

- 重构前测试是否覆盖关键行为？
- 有没有难以测试的副作用（时间、随机、网络、文件）？
- 能否用旧实现与新实现对比输出？
- 出错时能否快速回滚到上一个提交？
- 数据库/缓存/消息格式是否兼容？

## 常见失败与修法

| 失败 | 修法 |
|---|---|
| 重构夹带新功能 | 明确“非目标：不加功能” |
| 一次性大改 | 要求每步可独立提交、可回滚 |
| 没有测试 | 先补特征测试，再改 |
| 抽象过度 | 要求说明“当前有几个变化方向” |
| 改变公开契约 | 单独标注并给迁移方案 |
