# 调试与排错

> 场景：出现报错、偶发失败、性能异常、行为不符合预期。
> 适用：有可观察现象，但根因不明。
> 不适用：需求本身没定义清楚；那先回需求澄清。
> 关键原则：**先复现，再假设，一次只验证一个变量**。

## 可直接复制的提示词

```text
# 1. 角色与目标
你是一名擅长系统性排错的资深工程师，熟悉 Java、Spring Boot、MySQL、Redis、Linux。
本次唯一目标：定位下面问题的根因，并给出最小修复与回归验证。
目标受众：能执行命令、查看日志、修改代码的开发者。

# 2. 上下文
【项目卡】
{{PROJECT_CARD}}

【现象】
{{TASK：什么操作、什么结果、期望什么}}

【证据】
{{INPUT：完整报错、堆栈、日志、相关代码、复现步骤、环境版本}}

# 3. 输入与前置检查
若缺少“可复现步骤”“完整堆栈”“最近改动”中的任意一项，先问我，最多 3 个问题。
无法复现时，不要猜根因；先列出还需要哪些观测数据。

# 4. 执行步骤
1. 复述现象：触发条件、实际结果、期望结果、影响范围。
2. 判断问题层级：前端、接口、业务逻辑、数据、依赖、基础设施。
3. 列出 2–4 个可能原因，按可能性与验证成本排序。
4. 为每个原因设计一个成本最低的验证实验，说明看什么证据。
5. 每次只改一个变量；记录实验结果，排除或确认假设。
6. 给出根因解释：为什么之前没发现，为什么现在触发。
7. 给出最小修复 diff，并补一条能复现该 bug 的回归测试。
8. 给出预防建议：监控、断言、日志、边界校验。

# 5. 约束与非目标
- 不允许“把所有可疑地方都改一遍”。
- 不在没有证据时下根因结论；不确定的假设标【推断】。
- 不修改无关代码，不顺便优化性能。
- 涉及数据修复、缓存清理、重启服务时，先说明影响并等我确认。
- 不把日志中的敏感信息原样输出。

# 6. 输出格式
## 现象复述
## 证据
| 观察 | 来源 | 说明 |
## 假设与验证
| # | 假设 | 验证方法 | 结果 | 结论 |
## 根因
## 最小修复
## 回归测试
## 预防建议
## 仍未验证
总篇幅不超过 1000 字，代码和日志除外。

# 7. 示例
不要写：“可能是缓存问题，清一下缓存试试。”
要写：“假设是缓存击穿导致数据库瞬时压力。验证：查看 Redis 命中率与同一时刻慢查询数量；
若命中率骤降且慢查询上升，则支持该假设；否则排除。”

# 8. 验收标准与自检
- [ ] 有明确复现步骤，或明确说明无法复现及原因。
- [ ] 每个假设都有对应验证方法，而不是凭感觉。
- [ ] 根因能解释全部关键证据，不只解释一部分。
- [ ] 修复是最小改动，且有回归测试。
- [ ] 明确说明修复后如何确认问题不再出现。
- [ ] 未验证的推断已标注。

# 9. 下一步
输出后问我：先验证某个假设、直接给修复、还是补观测手段。
不要在我确认根因前大范围改代码。
```

## 使用说明

- 报错信息要完整：异常类型、消息、堆栈、触发请求、时间点。
- 偶发问题要附时间分布、并发量、最近发布记录。
- 如果模型一上来就给修复，回复：“先列假设和验证方法，不要改代码。”

## 排错记录模板

```text
时间：
现象：
影响范围：

```

## 常见失败与修法

| 失败 | 修法 |
|---|---|
| 盲改多处 | 要求“一次只验证一个假设” |
| 把推断当根因 | 要求“根因必须解释全部关键证据” |
| 修了但不防回归 | 要求补一条能复现 bug 的测试 |
| 忽略环境差异 | 提供 JDK/框架/数据库版本与部署方式 |
| 日志不足 | 先加最小观测，不要继续猜 |

## 高危操作提醒

以下操作必须先确认影响范围：

- 删除或更新生产数据。
- 清空缓存、重建索引。
- 重启、回滚、扩容。
- 修改鉴权、支付、限流配置。
