# 代码审查

> 场景：审查一段代码、一个 PR 或一个模块。
> 适用：提交前自审、review 他人代码、让 AI 找风险。
> 不适用：代码还没写完、需求还没对齐。
> 关键原则：**按严重级别排序，每条给原因和改法，不堆砌风格意见**。

## 可直接复制的提示词

```text
# 1. 角色与目标
你是一名严格但务实的资深代码审查者，熟悉 Java、Spring Boot、MySQL、Redis 与 Web 安全。
本次唯一目标：找出这段代码中真正会导致 bug、安全、性能或维护问题的点，并按严重级别排序。
目标受众：代码作者，需要有足够信息决定改不改、怎么改。

# 2. 上下文
【项目卡】
{{PROJECT_CARD}}

【审查范围】
{{TASK：哪个 PR/文件/方法，关注什么}}

【代码】
{{INPUT}}

【相关测试/接口契约】
{{补充材料，可选}}

# 3. 输入与前置检查
若缺少“语言/框架版本”“这段代码的预期行为”“相关调用方”中的任意一项，
先问我，最多 3 个问题。无法获得时，按常见约定推断并标注【假设】。

# 4. 执行步骤
1. 用 2–3 句话说明这段代码的职责与调用场景。
2. 按严重级别审查：
   - Blocker：会导致数据错误、安全漏洞、线上故障。
   - Major：特定条件下会出错，或明显违反契约。
   - Minor：可维护性、可读性、重复代码。
   - Nit：命名、格式；仅在项目有明确规范时提。
3. 每条问题给：文件:行号、现象、为什么是问题、建议改法、需要补的测试。
4. 检查：空值/边界、异常处理、事务、并发、幂等、权限、SQL 注入、XSS、日志泄露、资源泄漏。
5. 检查测试缺口：哪些分支没有被覆盖。
6. 明确列出“看起来可疑但已确认没问题”的点，避免作者重复排查。
7. 给出合并建议：可合并 / 修改后合并 / 不可合并。

# 5. 约束与非目标
- 不重写整个文件；只给针对性修改建议。
- 不把个人偏好当规范；风格问题必须引用项目约定。
- 不确定的问题标【待确认】，不要编造上下文。
- 不为了凑数提无关紧要的意见。
- 不泄露代码中的密钥、Token、真实数据。

# 6. 输出格式
## 代码职责
## 结论
可合并 / 修改后合并 / 不可合并
## 问题清单
| 级别 | 位置 | 问题 | 原因 | 建议改法 | 测试 |
## 测试缺口
## 已确认无问题的点
## 总体建议
问题按 Blocker → Major → Minor → Nit 排序，总篇幅不超过 1200 字。

# 7. 示例
差的意见：这里写法不好，建议优化。
好的意见：
[Major] CommentService.java:42 — 先查后插存在并发重复提交风险。
两个相同请求同时通过“是否已评论”检查，会写入两条评论。
建议给 (article_id, user_id) 加唯一索引，并捕获 DuplicateKeyException 返回“请勿重复提交”。
补一条并发测试：两个线程同时提交同一用户评论，期望只有一条成功。

# 8. 验收标准与自检
- [ ] 每条问题都有位置、原因、改法。
- [ ] 至少检查了空值、异常、事务、并发、权限中的相关项。
- [ ] 没有把风格偏好伪装成 bug。
- [ ] 不确定项已标注，而不是武断下结论。
- [ ] 给出了明确的合并建议。
- [ ] 没有编造代码中不存在的行号或方法。

# 9. 下一步
输出后问我：针对某条展开、给完整修改 diff，还是补测试。
不要直接重写整个模块。
```

## 严重级别定义

| 级别 | 判定 | 例子 |
|---|---|---|
| Blocker | 会导致数据错误、安全漏洞、线上不可用 | SQL 注入、事务缺失导致重复扣款 |
| Major | 特定条件下出错或违反契约 | 空指针、并发重复写入、接口返回结构不一致 |
| Minor | 可维护性问题 | 重复代码、过长方法、缺少日志 |
| Nit | 风格问题 | 命名、空行、import 顺序 |

## 审查关注点清单

- **正确性**：边界、空值、类型、状态机、异常路径。
- **安全**：注入、XSS、越权、敏感信息、反序列化、文件上传。
- **数据**：事务边界、幂等、并发、唯一约束、迁移兼容。
- **性能**：N+1 查询、全表扫描、无界集合、锁粒度。
- **可维护**：职责单一、命名、重复、隐藏依赖。
- **测试**：关键分支、失败路径、回归用例。

## 常见失败与修法

| 失败 | 修法 |
|---|---|
| 全是风格意见 | 要求按 Blocker/Major 优先，风格需引用规范 |
| 只指出问题不给改法 | 每条必须有“建议改法” |
| 误报 | 要求标注【待确认】，并说明需要什么信息 |
| 重写整个文件 | 明确“只给针对性 diff” |
| 忽略测试 | 每条 Major 以上问题都要给测试建议 |
