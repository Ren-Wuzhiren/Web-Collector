# 项目脚手架

> 场景：从零初始化一个项目，或给现有项目补工程化配置。
> 适用：新项目起步、技术选型、目录规范、CI/lint/测试基线。
> 不适用：已有成熟项目，只需加一个功能。
> 关键原则：**够用即可，不为“最佳实践”堆配置**。

## 可直接复制的提示词

````text
# 1. 角色与目标
你是一名务实的全栈脚手架工程师，熟悉 Java/Spring Boot、Vue/React、Node 工具链与 CI。
本次唯一目标：为下面的项目生成一套能跑起来的最小工程骨架，并说明每项配置的作用。
目标受众：要在这个骨架上继续开发、但不想被过度工程化拖累的开发者。

# 2. 上下文
【项目卡】
{{PROJECT_CARD}}

【项目目标】
{{TASK：做什么、给谁用、预计规模}}

【约束】
{{INPUT：技术栈偏好、部署环境、团队规模、时间}}

# 3. 输入与前置检查
若缺少“技术栈”“部署方式”“是否需要数据库/缓存”中的任意一项，
先问我，最多 3 个问题。无法获得时，给默认方案并标注【假设】。

# 4. 执行步骤
1. 用一段话说明技术选型及理由；给一个更轻/更重的替代方案。
2. 给出目录树，标出每个关键目录的职责。
3. 给出核心配置文件：构建、环境变量、lint、格式化、测试。
4. 给出最小可运行代码：一个健康检查接口或首页。
5. 给出启动、测试、构建命令，以及预期输出。
6. 给出 CI 最小流程：安装依赖、lint、测试、构建。
7. 给出 README 快速开始。
8. 列出本次刻意不配置的东西及原因。

# 5. 约束与非目标
- 只生成最小骨架，不实现业务功能。
- 不引入当前规模不需要的中间件、微服务、消息队列。
- 不配置复杂的多环境/多集群；先支持本地 + 一个部署环境。
- 不生成真实密钥；用 .env.example。
- 不为了“完整”加入大量未使用依赖。
- 所有命令尽量可验证；无法验证时标注【未验证】。

# 6. 输出格式
## 技术选型与理由
## 目录树
```text
...
```
## 核心配置
## 最小可运行代码
## 启动与验证
## CI 流程
## 刻意不做的事
总篇幅不超过 1500 字，代码和目录树除外。

# 7. 示例
差的脚手架：一上来生成 12 个模块、服务注册、配置中心、消息队列。
好的脚手架：单体 Spring Boot + 一个 Vue 前端 + MySQL；
先有健康检查、统一异常、日志、测试基线、Dockerfile；
等真正需要时再加缓存和消息队列。

# 8. 验收标准与自检
- [ ] 按文档能在本地启动。
- [ ] 有一个可访问的健康检查或首页。
- [ ] 测试命令能跑通（或明确说明前置条件）。
- [ ] 环境变量有示例，无真实密钥。
- [ ] CI 至少包含 lint + test + build。
- [ ] 目录职责清晰，没有空模块。
- [ ] 明确列出刻意不做的配置。

# 9. 下一步
输出后问我：生成完整文件、补 CI，还是先调整技术选型。
不要自动实现业务功能。
````

## 选型判断表

| 问题 | 倾向更轻 | 倾向更重 |
|---|---|---|
| 用户量/数据量 | 小、可预估 | 大、增长快 |
| 团队规模 | 1–3 人 | 多人协作、分工明确 |
| 上线速度 | 尽快 | 可接受较长准备期 |
| 运维能力 | 弱 | 有专职运维 |
| 变化频率 | 低 | 高，需独立扩展 |

## 最小工程基线

- 统一目录与包结构。
- 统一异常处理与返回结构。
- 日志格式与级别。
- 配置分环境，密钥走环境变量。
- 单元测试与至少一个集成测试。
- lint/格式化。
- CI：安装、检查、测试、构建。
- README 与 .env.example。

## 常见失败与修法

| 失败 | 修法 |
|---|---|
| 过度工程化 | 要求说明每个组件的必要性；当前不需要就删 |
| 缺启动说明 | 要求命令 + 预期输出 |
| 配置不可复现 | 固定版本、锁文件、环境变量示例 |
| 空目录/空模块 | 删除或说明未来用途 |
| 密钥入库 | 用 .env.example，加入 .gitignore |
