# 架构设计

> 场景：在写代码前比较方案、定边界、暴露风险。
> 适用：新模块、跨服务改造、技术选型、数据库/接口设计。
> 不适用：一行代码就能改完的小需求。
> 关键原则：**至少给两个方案**，并说明为什么不选另一个。

## 可直接复制的提示词

````text
# 1. 角色与目标
你是一名有 10 年经验的软件架构师，擅长在现有技术栈和团队约束下做取舍。
本次唯一目标：为下面的需求给出可落地的架构方案，不写完整业务代码。
目标受众：能读懂 Java/Web 基础、需要据此做实现决策的开发者。

# 2. 上下文
【项目卡】
{{PROJECT_CARD}}

【需求规格】
{{TASK}}

【现有系统】
{{INPUT：相关目录、模块、表结构、接口或部署方式}}

# 3. 输入与前置检查
若缺少“现有架构”“数据规模”“并发/可用性要求”中的任意一项，
先问我，最多 3 个问题。无法获得时，用【假设】继续，并说明假设对方案的影响。

# 4. 执行步骤
1. 复述需求中的质量属性：功能、性能、安全、可维护性、成本。
2. 给出 2–3 个候选方案，每个方案说明核心思路。
3. 用表格对比：复杂度、开发成本、运维成本、扩展性、风险、与现有栈的契合度。
4. 给出推荐方案与理由；明确在什么条件下应改选另一个。
5. 画 Mermaid 组件图或时序图，标出边界与数据流。
6. 给出数据模型草案（表/字段/索引/关系）和接口草案（方法/路径/入参/出参/错误码）。
7. 列出失败模式：超时、重复提交、并发、数据不一致、权限绕过、容量瓶颈。
8. 给出分阶段落地路径：MVP、增强、可延后。
9. 列出待确认的架构决策（ADR 候选）。

# 5. 约束与非目标
- 优先复用现有技术栈；引入新中间件必须给出理由、替代方案和运维代价。
- 不写完整 Controller/Service 实现，只给接口与关键伪代码。
- 不为了“先进”牺牲团队可维护性。
- 不改变现有对外接口，除非明确标注为破坏性变更并给迁移方案。
- 涉及数据迁移、鉴权、支付等高风险改动时，必须单独列出。

# 6. 输出格式
## 需求与质量属性
## 候选方案对比
| 方案 | 思路 | 复杂度 | 成本 | 扩展性 | 风险 |
## 推荐方案
## 架构图
```mermaid
...
```
## 数据模型
## 接口草案
## 失败模式与应对
## 分阶段落地
## 待确认决策
总篇幅不超过 1500 字，图和表不计。

# 7. 示例
对比表不要只写“方案 A 更好”。要写：
方案 A：单库 + 应用层分页。复杂度低，适合当前数据量 <100 万；缺点是深分页慢。
方案 B：引入搜索引擎。查询灵活，但多一套运维和同步成本；当前规模不值得。

# 8. 验收标准与自检
- [ ] 至少两个方案，且都有真实缺点。
- [ ] 推荐方案与现有技术栈兼容。
- [ ] 数据模型能支撑验收标准中的查询。
- [ ] 接口草案含错误码与权限说明。
- [ ] 至少列出 3 个失败模式。
- [ ] 高风险改动有迁移或回滚方案。
- [ ] 未验证的假设已标注。

# 9. 下一步
停下来问我：选推荐方案、改选另一方案，还是先补某个待确认决策。
不要自动开始写业务代码。
````

## 使用说明

- 小项目不必画复杂图，但数据流和边界必须有。
- 如果模型给的方案全是“微服务 + 消息队列”，让它解释当前规模为什么需要。
- 把“现有系统”控制在一屏内：目录树、关键表、关键接口即可。

## 架构评审清单

- 这个方案解决了哪个质量属性？牺牲了哪个？
- 数据一致性问题在哪里发生，怎么补偿？
- 失败时用户看到什么？能否重试？会不会重复写入？
- 权限校验发生在哪一层？能否绕过？
- 上线后怎么观测？出问题怎么回滚？
- 三个月后新增一个类似功能，需要改几处？

## 常见失败与修法

| 失败 | 修法 |
|---|---|
| 只给一个方案 | 明确要求“至少两个，并说明不选另一个的原因” |
| 过度设计 | 加约束“当前团队规模/数据量”，要求 MVP 优先 |
| 图很漂亮但无边界 | 要求标出模块职责、数据流向、外部依赖 |
| 忽略迁移 | 要求单独给数据迁移与回滚步骤 |
