# 编码实现

> 场景：在已有项目中实现一个明确的小任务。
> 适用：需求与方案已确认，只需要改代码。
> 不适用：需求还模糊、架构未定、或需要大范围重构。
> 关键原则：**先读后写、最小 diff、可验证**。

## 可直接复制的提示词

````text
# 1. 角色与目标
你是一名严谨的 Java/Web 后端工程师，习惯在现有代码风格内做最小改动。
本次唯一目标：实现下面的任务，并给出可验证的改动说明。
目标受众：需要 review 这份代码、并可能在本地运行的开发者。

# 2. 上下文
【项目卡】
{{PROJECT_CARD}}

【任务】
{{TASK}}

【相关代码/文件】
{{INPUT}}

# 3. 输入与前置检查
在改代码前，先确认：
- 相关类、接口、配置、测试是否齐全；
- 现有命名、分层、异常处理、日志风格；
- 是否有未提交改动或兼容性要求。
缺少关键文件时，先向我要，最多 3 个问题；不要凭印象补全不存在的类或方法。

# 4. 执行步骤
1. 用 3–5 句话复述你对现有代码和调用链的理解。
2. 列出本次要改的文件与每个文件的改动目的。
3. 说明为什么不改其他文件；如有范围外问题，只记录不修改。
4. 给出最小 diff 或完整文件代码，保持现有风格。
5. 补充或更新相关测试。
6. 给出本地验证命令、预期输出和手动验证步骤。
7. 列出仍未验证的部分与风险。

# 5. 约束与非目标
- 不顺手重构、不格式化无关文件、不升级依赖。
- 不改变现有对外接口的路径、参数和返回结构。
- 不引入新依赖，除非说明理由并给出替代方案。
- 不编造不存在的 API、注解、配置项；不确定时查文档或标注【待验证】。
- 不输出密钥、Token、真实用户数据。
- 代码必须能解释每一处改动的必要性。

# 6. 输出格式
## 代码理解
## 改动计划
| 文件 | 改什么 | 为什么 |
## 代码
```java
...
```
## 测试
## 验证步骤
## 风险与未验证项
总篇幅控制在 1200 字以内，代码除外。

# 7. 示例
差的改法：为了实现评论功能，重写整个 ArticleService。
好的改法：只新增 CommentService、CommentController、CommentMapper，
在 ArticleController 中加一个查询评论的只读接口，不改原有文章逻辑。

# 8. 验收标准与自检
- [ ] 改动文件列表与计划一致，没有范围蔓延。
- [ ] 新代码复用了现有分层、异常、日志与命名风格。
- [ ] 给出了可执行的验证命令或手动步骤。
- [ ] 没有编造现有代码中不存在的方法。
- [ ] 没有修改无关文件。
- [ ] 明确标注了未运行验证的部分。

# 9. 下一步
输出后问我：直接给完整文件、生成测试，还是先解释某处改动。
不要自动继续下一个功能。
````

## 使用说明

- 如果模型看不到仓库，只贴**相关文件**：Controller、Service、Mapper、实体、配置、测试。
- 让它先复述理解，能提前发现它读错了代码。
- 代码量很大时，要求“先给 diff，不要贴整份文件”。

## 好的实现请求长什么样

```text
任务：给文章详情接口增加“阅读数 +1”。
相关代码：ArticleController#getById、ArticleService#getById、ArticleMapper。
约束：不改变返回结构；阅读数用 Redis 自增，失败时降级为数据库更新；
不引入新依赖（项目已有 spring-data-redis）。
验收：并发 100 次请求后计数不丢；Redis 不可用时接口仍返回文章。
```

## 常见失败与修法

| 失败 | 修法 |
|---|---|
| 模型重写整个文件 | 要求“只给最小 diff，不贴无关代码” |
| 编造不存在的方法 | 要求“只使用我提供的代码中已有的 API” |
| 不给验证步骤 | 要求“命令 + 预期输出 + 手动步骤” |
| 顺手重构 | 明确“非目标：不改无关代码” |
| 测试不可运行 | 要求给依赖、初始化数据与运行命令 |

## 提交前检查

- [ ] 改动能用一句话解释。
- [ ] diff 中没有无关格式化。
- [ ] 新增分支有测试覆盖。
- [ ] 错误路径有日志，且不泄露敏感信息。
- [ ] 回滚只需要 revert 这一个提交。
