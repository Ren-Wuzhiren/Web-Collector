# 提示词评分表与失败模式

用于两件事：改造提示词时自检；比较“裸提示词”和“系统提示词”的输出质量。

## 评分表（每项 0–2 分，共 20 分）

| # | 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|---|
| 1 | 目标单一性 | 目标含糊或多个目标混杂 | 有目标但边界不清 | 一句话说清唯一目标与非目标 |
| 2 | 上下文充分性 | 没有项目/学习者背景 | 有背景但缺关键约束 | 只含相关上下文，足够做判断 |
| 3 | 角色具体性 | “你是专家” | 有技术栈但无经验/受众 | 具体经验 + 任务 + 目标受众 |
| 4 | 步骤可执行性 | 只有“帮我做” | 有步骤但缺顺序/停止条件 | 编号步骤，含暂停与确认点 |
| 5 | 约束可检验性 | 只有“写好一点” | 有约束但无法验证 | 硬约束、非目标、取舍规则清晰 |
| 6 | 输出格式明确性 | 没有格式要求 | 说了结构但不具体 | 标题/表格/篇幅/代码块都明确 |
| 7 | 示例有效性 | 无示例且任务需要示例 | 有示例但过长或偏题 | 短小、典型、说明好坏 |
| 8 | 验收标准 | 无 | 有笼统标准 | 可勾选、可运行、可判定 |
| 9 | 不确定性处理 | 鼓励自信输出 | 提到“不确定要说” | 规定标注格式、追问上限、假设处理 |
| 10 | 篇幅与优先级 | 冗长或关键约束被淹没 | 偏长但可读 | 关键约束首尾呼应，长度合适 |

**判定**

- 18–20：可直接长期使用。
- 16–17：可用，建议小改。
- 12–15：需要重写部分段落。
- 0–11：不要直接使用。

## 失败模式库

| 失败模式 | 典型症状 | 根因 | 修法 |
|---|---|---|---|
| 角色过载 | 模型什么都做，但都不深 | 角色太宽泛 | 缩到具体技术栈与阶段 |
| 上下文过载 | 模型忽略关键约束 | 整份仓库/长文直接粘贴 | 只留相关片段，项目卡外置 |
| 指令打架 | 输出自相矛盾 | 同时要求兼容与升级、详细与简短 | 写优先级与取舍规则 |
| 没有停点 | 一口气做完，方向错了才返工 | 缺确认点 | 在步骤中插入“停下确认” |
| 格式漂移 | 每次输出结构不同 | 格式要求模糊 | 给标题、表格列、字数 |
| 假验证 | 声称“已测试通过” | 没有运行环境却要求验证 | 要求标注“未运行验证” |
| 学习幻觉 | 看了解释就以为会了 | 没有主动回忆与练习 | 苏格拉底卡 + 间隔复习 |
| 范围蔓延 | 修 bug 变成重构 | 没有非目标 | 明确“本轮只做” |
| 示例绑架 | 输出照抄示例 | 示例太具体或只有一个 | 给反例，或明确“仅示意” |
| 长对话失忆 | 后面忘了前面的约束 | 上下文漂移 | 每阶段重贴项目卡与约束 |

## 改造优先级

时间有限时，按这个顺序改，收益最高：

1. 加**非目标**（防止范围蔓延）。
2. 加**验收标准**（让“做完”可判定）。
3. 把**角色缩具体**（提升专业度）。
4. 加**停止条件**（防止一路错到底）。
5. 规定**输出格式**（减少返工）。
6. 最后才优化措辞和语气。

## A/B 测试方法

同一任务，准备两份提示词：

- A：你原来会直接发的裸提示词。
- B：本系统的场景卡，填入同样的项目卡与任务。

各自只跑一次，避免反复挑选“好看的结果”。按评分表打分，并记录：

| 项目 | A | B |
|---|---|---|
| 是否主动追问关键信息 | | |
| 是否给出可执行步骤 | | |
| 是否给出验收标准 | | |
| 是否有编造/未标注的推断 | | |
| 输出是否可直接使用 | | |
| 总分 /20 | | |

**注意**：一次结果不足以证明优劣。至少换 2 个任务、2 个模型再下结论。
