# 提示词解剖：C.R.A.F.T.+ 九段式

所有场景卡都使用同一套骨架。它的作用是让模型知道：**你是谁、为什么做、依据什么做、怎么做、做到什么程度、交什么格式、怎么算合格**。

## C.R.A.F.T.+ 对照

| 骨架段落 | 对应要素 | 回答的问题 |
|---|---|---|
| 1 角色与目标 | Role / Target Audience | 你以什么身份、为谁、完成什么 |
| 2 上下文 | Context | 项目、代码、学习者背景是什么 |
| 3 输入与前置检查 | Input | 我给了什么、还缺什么 |
| 4 执行步骤 | Action | 按什么顺序做、何时停下 |
| 5 约束与非目标 | Constraints | 不能做什么、不做什么 |
| 6 输出格式 | Format | 交付物长什么样 |
| 7 示例/反例 | Examples | 什么叫好、什么叫不好 |
| 8 验收与自检 | Acceptance | 怎么判断合格 |
| 9 下一步 | Iteration | 合格后进入哪里 |

## 九段式逐段写法

### 1. 角色与目标

**写法**：具体身份 + 本次唯一目标 + 目标受众。

```text
你是一名有 10 年经验的 Java 后端工程师，擅长 Spring Boot 与 MySQL 性能调优。
本次唯一目标：帮我在不改变接口契约的前提下，定位这个接口偶发 500 的根因。
目标受众：能读懂 Java 代码、但没接触过这个项目的开发者。
```

避免：“你是一个无所不能的专家。” 角色越宽泛，输出越平庸。

### 2. 上下文

**写法**：项目卡 + 与本次任务直接相关的代码/报错/数据。

```text
【项目卡】
技术栈：Java 17、Spring Boot 3.2、MySQL 8.0、Redis 7
约定：Controller 不写业务逻辑；异常统一由 GlobalExceptionHandler 处理
相关代码：{{粘贴 Service 与 Mapper 的最小片段}}
报错：{{完整堆栈，已脱敏}}
```

上下文不是越多越好。只放**会改变判断**的信息。

### 3. 输入与前置检查

**写法**：列出已有输入；定义缺失时的行为。

```text
【已有输入】接口代码、错误日志、数据库表结构。
【前置检查】如果缺少复现步骤或完整堆栈，先问我，不要猜。
【最多追问】3 个问题，按重要性排序。
```

### 4. 执行步骤

**写法**：编号、可执行、带停止条件。

```text
1. 复述你对请求链路和失败点的理解。
2. 列出 2–3 个可能原因，按可能性排序。
3. 为每个原因设计一个成本最低的验证方法。
4. 等我确认后再改代码。
5. 修复后给出回归测试。
```

步骤中要写“何时停”：例如“信息不足时停在第 1 步提问”“涉及数据库结构变更时先确认”。

### 5. 约束与非目标

**写法**：硬约束、软约束、明确不做的事。

```text
【硬约束】
- 不改变现有 HTTP 接口的路径、参数和返回结构。
- 不升级 Spring Boot 版本。
- 不引入新的第三方依赖。
【非目标】
- 不重构整个 Service。
- 不处理与本 bug 无关的日志规范问题。
```

非目标是控制范围蔓延的关键。没有它，模型很容易“顺便优化”。

### 6. 输出格式

**写法**：规定结构、篇幅、代码块、表格列名。

```text
按以下结构输出：
## 结论
一句话说明最可能根因。
## 证据
| 证据 | 来源 | 说明 |
## 修复方案
给出最小 diff，并解释为什么这样改。
## 验证
列出命令、预期结果和回归测试。
## 风险
列出仍未验证的假设。
总篇幅不超过 800 字，代码除外。
```

格式越具体，返工越少。但不要为了格式牺牲内容。

### 7. 示例/反例

**写法**：给一个短小、有代表性的正例；必要时给一个反例并说明为什么错。

适用于：代码审查、概念讲解、写作、数据提取、格式转换。

不适用于：探索性架构讨论（过早示例会限制思路）。

### 8. 验收与自检

**写法**：可勾选清单，交付前逐项检查。

```text
交付前自检：
- [ ] 结论有证据支撑，未把推断写成事实。
- [ ] 修复只改了必要文件。
- [ ] 给出了可执行的验证命令。
- [ ] 明确标注了未验证的部分。
- [ ] 没有引入新依赖或接口变更。
```

### 9. 下一步

**写法**：说明合格后进入哪个场景，或让用户选择。

```text
如果你确认根因，我下一步可以：
A. 输出修复 diff；
B. 补回归测试；
C. 分析同类接口是否有相同问题。
请选一个，不要一次全做。
```

## 变量字典

| 变量 | 必填 | 说明 | 示例 |
|---|---|---|---|
| `{{PROJECT_CARD}}` | 开发轨建议 | 项目上下文 | 技术栈、目录、约定、命令 |
| `{{LEARNER_CARD}}` | 学习轨建议 | 学习者背景 | 已学课程、目标、时间 |
| `{{TASK}}` | 是 | 本次任务 | “给博客加评论功能” |
| `{{INPUT}}` | 视情况 | 原始材料 | 代码、报错、文档、题目 |
| `{{CONSTRAINTS}}` | 否 | 额外限制 | 不升级版本、两周内完成 |
| `{{OUTPUT_FORMAT}}` | 否 | 覆盖默认格式 | “用表格输出” |
| `{{ACCEPTANCE}}` | 否 | 覆盖默认验收 | “必须通过现有测试” |
| `{{DEADLINE}}` | 否 | 时间预算 | “今天 2 小时” |

变量用双花括号。若使用的平台会把花括号当模板语法，替换成 `【项目卡】` 等中文标记即可。

场景卡里还会出现 `{{主题}}`、`{{概念}}`、`{{项目名}}`、`{{阶段}}` 这类**局部变量**，按当前卡片说明直接替换即可，不必全部登记到上表。

`{{INPUT：说明}}`、`{{TASK：说明}}` 是带填写提示的写法：变量名仍是 `INPUT` / `TASK`，冒号后的文字告诉你该填什么。实际使用时，把整段（含说明）替换成真实内容。

## 长度与顺序

- **场景卡正文**：约 800–1200 个中文字。超过就拆分场景，或把细节移到项目卡。
- **项目卡**：可以长，但只贴相关片段；不要整份仓库。
- **关键约束**：开头和结尾各出现一次，利用首因与近因效应。
- **输出格式**：放在靠后位置，紧邻执行指令，模型更容易遵守。
- **示例**：放在任务说明之后、验收之前，避免模型把示例当成唯一答案。

## 组装模板

```text
# 1. 角色与目标
你是 {{ROLE}}。本次唯一目标：{{GOAL}}。目标受众：{{AUDIENCE}}。

# 2. 上下文
{{PROJECT_CARD 或 LEARNER_CARD}}
{{相关材料}}

# 3. 输入与前置检查
已有：{{INPUT}}
缺少 {{关键信息}} 时，先问我，最多 3 个问题。

# 4. 执行步骤
1. ...
2. ...
3. 涉及 {{高风险操作}} 时停下确认。

# 5. 约束与非目标
硬约束：{{CONSTRAINTS}}
非目标：{{NON_GOALS}}

# 6. 输出格式
{{FORMAT}}

# 7. 示例
{{EXAMPLE（可选）}}

# 8. 验收与自检
- [ ] {{ACCEPTANCE_1}}
- [ ] {{ACCEPTANCE_2}}

# 9. 下一步
{{NEXT_STEP}}
```

## 常见错误

| 错误 | 表现 | 修法 |
|---|---|---|
| 角色万能 | “你是全栈专家” | 缩到具体技术栈与任务 |
| 上下文过载 | 粘贴整个仓库 | 只留相关文件与报错 |
| 指令冲突 | 既要兼容旧版又要用新 API | 明确优先级与取舍 |
| 没有停止条件 | 模型一路做到底 | 在步骤中写“停下确认” |
| 没有验收 | 输出完就结束 | 加可勾选清单 |
| 格式模糊 | “详细一点” | 规定标题、表格列、字数 |
| 学习与开发混用 | 既要代码又要讲解 | 拆成两张卡，先做后讲 |

## 改造一张旧提示词的方法

1. 标出它现在包含九段中的哪几段。
2. 补“非目标”和“验收标准”——这两项收益最大。
3. 把角色从“专家”缩到“具体经验 + 具体任务”。
4. 把长上下文移到项目卡。
5. 用评分表打一次分，低于 16 分就继续改。
